# Work: deployments

Reference detail moved word for word from `wikantik-work/CLAUDE.md`. The invariants are in that file; where a class Javadoc states a rule, the Javadoc is the authority. Read this before changing the area.

Phase 4. Plan: `docs/superpowers/plans/2026-11-16-work-management-phase4-deployments.md` (its "Decisions" D1–D11 were approved by the owner).

- **A deployment has no project.** It is one product version going to an environment, carrying items (`work_deployment`, `work_deployment_item`, V082). Its history is its own append-only table (`work_deployment_event`), because `work_event` needs a project; each carried item still gets `deployment_requested`, `shipped` and `rolled_back` events (`from_value` `deployment:<id>`).
- **It is seen through what it carries.** `DeploymentAccess` is the only place deployments meet standing: it asks `WorkStanding` for the actor's role in every project a carried item belongs to. A caller who can see none of the items gets `WorkNotFoundException`, the same as for an unknown id. `WorkDeploymentsService` hands out `DeploymentView`s whose `deployment.itemIds()` holds **only the visible items**: never return a raw `Deployment` from the store to a caller, or hidden ids and their count leak. `WorkDeploymentAccessPostgresTest`.
- **States only move forward** (`DeploymentState.mayBecome`): requested, approved, running, verified or failed, then rolled back; requested or approved may instead become rejected (the requester withdraws it, or someone who may approve turns it down; without this the only way to clear a mistaken request was to approve it, which opens the script gate). A deployment carries only items that are `ready` or later and target its product. The store decides the move on the locked row (`bad_transition`). Verified needs non-blank evidence (the service and a table CHECK both say so); evidence is plain text and no surface may render it as markup.
- **The deploy gate** (`DeployGates.mayApprove`) is the product's `deploy_gate`, never the autonomy level: `human` = an admin or a person who leads every carried project; `agent` = also any member of every carried project. Requesting and running take membership of every carried project. An agent's approval decision is reported as gate `deploy`.
- **Done means in production.** `ItemGates.requireStatusChange` returns `CloseRules(ackRequired, needsDeployment)`; `needsDeployment` is true for any actor closing a story or task whose epic's done-means is `in_production`. The store checks for a verified deployment with the item row locked (`JdbcWorkItemWrites.requireShipped`, conflict `awaiting_deployment`). "Shipped" (`JdbcWorkDeployments.shippedVerified`) means: environment `production`, state verified, verified at or after the item's last merged change, and a deployment of the product the item targets now. A rolled-back deployment no longer counts; an already closed item stays closed. **Leaving the epic is a loosening**: `ItemGates.requireNoLoosening` treats a move that takes an item from `in_production` to `merged` like a looser level (a lead, never an agent); keep any new way of changing an item's parent behind it.
- **`gate(actor, id, version)`** is what the deploy script asks (`GET deployments/{id}/gate`), answered from one read: approved only for the same version in state approved or running, with the state, version and environment it was taken from (the script compares the environment). `cleared` is its boolean. It reads committed state, so an approval or failure not yet committed changes nothing. `WorkDeploymentRacePostgresTest`.
- **`wikantik_work_deployments_total{state}`**: no product label.
- `closed_at` is set by every state that ends a deployment (`DeploymentState.ended()`: verified, failed, rejected, rolled back). `forProduct` reads a page at a time until it has the visible deployments asked for. What a caller may type is checked in `DeploymentInputs` (split from the service for the complexity limit).
