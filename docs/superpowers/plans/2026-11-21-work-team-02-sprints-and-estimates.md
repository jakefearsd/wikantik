# Work Management for Small Teams — Part 2: Sprints and estimates — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A project lead plans time-boxed sprints, members put estimated stories and tasks in them, starting a sprint records what was committed, closing it records what was completed and moves the rest, and anyone in the project sees a burndown and velocity computed from the event log.

**Architecture:** A new facade `WorkService.features().sprints()` (`WorkSprintsService`) over a new store `WorkStore.sprints()` (`WorkSprintStore`, `JdbcWorkSprints`), modelled on deployments. `work_item` gains two nullable columns (`sprint_id`, `estimate`) carried on `Item` and written by the existing item write, whose changes are ordinary `field` events. Burndown is a pure function (`Burndown`) replaying those events; no table stores a figure except the four commitment and completion numbers on the sprint row, which are a record of a promise.

**Tech Stack:** Java 25, PostgreSQL 18 (`Jdbc`, `PostgresTestDb`, `FaultInjectingDataSource`), JUnit 5, Mockito, React 19 + vitest (inline SVG chart), Cargo/Selenide ITs.

**Spec:** docs/superpowers/specs/2026-11-21-work-team-features-design.md, section 2 (decisions D2–D5); index and global constraints: docs/superpowers/plans/2026-11-21-work-team-features.md

**Depends on:** Part 1 (`docs/superpowers/plans/2026-11-21-work-team-01-labels-and-type.md`) complete. Nothing of its behaviour is used, but this part appends to the records Part 1 extended and takes the next migration number:

- `ItemFilter` canonical constructor ending `…, String queue, WorkType type, Set<String> labels`, its 11-argument secondary constructor, `with`, `withQueue`; `JdbcWorkStore.board` rebuilds the scoped filter field by field; `WorkScopes.Scope.pin` builds the null-filter case.
- `WorkEventDiff.changeEvents` ending with the `type` and `labels` `fieldEvent` lines; `ItemPatchApplier.KEYS` containing `type`, `labels`.
- `V084` is taken; this part is `V085` (take the next free number at execution time).

## Decisions

- **P2-1. Policy lives in `WorkPolicy`, not a new `SprintGates` class.** Two actions: `MANAGE_SPRINT( LEAD, management, not fenced )` (create, update, start, close) and `PLAN_SPRINT( MEMBER, not management, not fenced )` (set an item's `sprint`). An agent is refused both with "A person plans a sprint.", before the role check, as `ACKNOWLEDGE` is. Estimating needs only `EDIT_ITEM`, which an agent may do on an item it may edit. Reason: one place decides who may do what, and the golden table pins it. If wrong: a class to extract; no behaviour changes.
- **P2-2. Lock order sprint rows, then item rows.** `start` and `close` take `FOR UPDATE` on their sprint rows (id order), then the items. An item write that changes `sprint`, `estimate` or `status` of an item that is or becomes part of a sprint first takes `FOR SHARE` on those sprint rows (id order), then the item row. Reason: the commitment and the completion are read with no concurrent change to what they count, and the order has no cycle. Cost if wrong: one extra statement on those writes only.
- **P2-3. "Before the start" and "before the close" are decided by event id, not time.** The store returns the ids of the `sprint_started` and `sprint_closed` events; a change counts as before the start when its event id is lower. Days are bucketed by `work_event.at`. Reason: `at` is the transaction's start time, so a write that waited on the sprint lock can carry an earlier `at` than the start it lost to; ids are taken after the lock (P2-2), so they order correctly. Cost if wrong: none visible to users.
- **P2-4. What the burndown replays.** `status` and `handoff` events (the status part), and `field` events noted `sprint` and `estimate`. Claim events are not replayed: they never move an item into or out of `done` or `cancelled`, which is all the burndown distinguishes. A `cancelled` item leaves scope; a null estimate counts one item and no points.
- **P2-5. Creating an item sets neither sprint nor estimate.** Both are set by a later patch, so `ItemDraft`, `createItem` and the MCP `create_item` stay as they are, and every sprint membership starts with a `field` event. If wrong: two optional draft fields and two extra events on create.
- **P2-6. Closed means closed.** A closed sprint cannot be edited (`sprint_closed`) and accepts no item (`sprint_closed`). An item may leave a closed sprint (a reopened item must be plannable again). The commitment, completion and burndown of a closed sprint do not move, because the burndown stops at the close event (P2-3).
- **P2-7. An epic's points** are the sum over its non-cancelled stories of the story's estimate, or, for a story with none, the sum of its non-cancelled tasks' estimates. Reason: no double counting when a team estimates both levels. A story asked the same returns the sum of its tasks; a task returns 0.
- **P2-8. Days are server-zone days.** `WorkWiring` passes `Clock.systemDefaultZone()` instead of `Clock.systemUTC()`; instants are unchanged, and `WorkSprintsService` takes the zone from the clock. Part 6's weeks use the same clock. If wrong: one line back.
- **P2-9. Sprint fields.** Name 1–60 characters after trimming, unique in the project (a duplicate is 400 `name`); goal at most 500 characters; both dates required, `endsOn` on or after `startsOn`. A planned sprint cannot be closed and is never deleted.
- **P2-10. Item JSON carries `sprintId` and `estimate`, not a sprint object.** The UI loads the project's sprint list once (it needs it for the selector anyway) and names the sprint from it; an epic's points come from `GET /api/work/items/{key}/points`, beside the item, as `policy` and `shipped-in` do. Reason: no per-item sprint lookup in every list response, and `ItemView`/`ItemSummary` stay as they are (they are built in every mock-based test). MCP `get_item` does name the sprint (one lookup per call).
- **P2-11. A fourth event, `sprint_updated`,** for name, goal or date edits, because every state change writes an event. Project-level sprint events have no item, `to_value` the sprint id, `note` the sprint's name after the change.
- **P2-12. Velocity** is the last six closed sprints by `closed_at`, returned oldest first, as `Velocity( sprintId, name, endsOn, committedItems, committedPoints, completedItems, completedPoints )`.
- **P2-13. Estimates are `BigDecimal` at scale 1 everywhere** (`Item`'s compact constructor normalises); event text is `stripTrailingZeros().toPlainString()` (`3`, `2.5`, `0`), so `3` and `3.0` are no change and write no event.
- **P2-14. Belt and braces in the schema:** a CHECK that an epic has neither sprint nor estimate, a CHECK that a sprint's timestamps and figures match its state, and a partial index for sprint `field` events.

## Deviations from the outline

1. **No `SprintGates` class.** Outline: `SprintGates.java` and `SprintGatesTest`. Here: two `Action` constants and one refusal in `WorkPolicy`, tested by `WorkPolicySprintTest` and the regenerated golden (P2-1). Why: `WorkPolicy` is the module's one role policy and its golden pins every action.
2. **`Burndown.of` signature.** Outline: `of( events, from, to, zone )` and `Day( date, remainingPoints, remainingItems, scopePoints )`. Here: `of( sprintId, events, from, to, beforeEventId, zone )`, `Day` adds `scopeItems`, plus `membersAt`. Why: the replay must know which sprint the `sprint` values mean, and must stop at the close event so the close's own moves do not empty the last day (P2-3).
3. **`eventsFor` returns `SprintHistory`** (events plus the start and close event ids) and takes the project id. Why: the ids are the cut-off (P2-3); the project id keeps the scans on the project's events.
4. **Item JSON.** Outline: `sprint: {id,name,state}` on every item and `childPoints` on an epic's JSON. Here: `sprintId` and `estimate` on the item, names from the project's sprint list, points from `GET items/{key}/points` (P2-10). Why: the house rule keeps `ItemView`/`ItemSummary` unchanged and adds reads beside the item; no per-item sprint lookup in lists.
5. **A fourth event type, `sprint_updated`.** Outline lists three. Why: an edit is a state change and must write an event (P2-11).
6. **Schema additions** beyond the outline DDL: `work_sprint_record_chk`, `work_item_epic_unplanned_chk`, `idx_work_event_sprint_moves`, and the `GRANT` (P2-14). The outline DDL itself is kept verbatim.
7. **Close target refusals** are one conflict `bad_target` for missing, self, closed and other-project targets; a target may only be planned (the one active sprint is the one closing).
8. **`WorkEventNames` gains nothing.** The global constraint asks for "a name in `WorkEventNames`" per new event type; the four sprint events carry no person, queue or agent value, which is all that class names. Their text is in `eventText.js`.
9. **`WorkWiring`'s clock** becomes `Clock.systemDefaultZone()` (P2-8). Not in the outline.
