Host: local bare-metal Tomcat 11, 10 cores, JVM pinned -Xms2g -Xmx2g G1.
k6 co-resident (so absolute RPS is k6-confounded; the signal is CPU
composition + p95, per the §15 precedent in docs/ScalingCharacterization.md).

## Iteration 1 — BasicAuthFilter session fast path was dead code

`BasicAuthFilter` compared the Basic-auth username against
`Session.getUserPrincipal()`, but `WikiSession.injectUserProfilePrincipals()`
sets that to the user's **FullName** (preferring `WikiPrincipal.FULL_NAME`);
the login name lives on `getLoginPrincipal()`. So `"testbot".equals("Test
Automation Bot")` — false on every request, for every user whose full name
differs from their login name. The "don't re-login on every request" guard had
never fired in production.

Fixed by matching either principal. Measured on a session-holding client:
**312 ms -> 1.6 ms** per admin request.

The aggregate profile did NOT move (96.01% still bcrypt), which was the
informative part: the harness — like monitoring pollers, cron jobs, CI scripts
and SDK one-shot calls — is stateless and carries no session cookie, so it
cannot use the fast path at all. That client class is the one that costs money.

## Iteration 2 — short-TTL successful-verification cache

`AbstractUserDatabase.validatePassword` now caches successful verifications,
mirroring `ApiKeyService.verifyCache` (§14.2 of ScalingCharacterization).

- Key: `loginName + ' ' + sha256Hex(password || storedHash)`. Binding the key
  to the stored hash means a password change rotates the key, so it takes
  effect **immediately** rather than after the TTL.
- Successes only — bcrypt's cost is a deliberate brute-force deterrent, so a
  wrong password always pays full price.
- Legacy-hash migration branch excluded (it mutates and saves the profile).
- Kill switch: `wikantik.auth.password.verifyCache.ttlSeconds=0`.
- Cannot bypass lockout: `UserDatabaseLoginModule` checks `profile.isLocked()`
  after and outside `validatePassword()`, against a freshly-fetched profile.

## Iteration 3 — HNSW docvalues acquired per leaf, not per hit

`LuceneHnswChunkVectorIndex.topKChunks` called
`ctx.reader().getSortedDocValues(...)` **twice per hit**. That is not a cheap
accessor — each call constructs a fresh `Lucene90DocValuesProducer$TermsDict`
with its own block buffers. At the shipped `wikantik.bundle.dense.top_k = 300`
that is up to **600 TermsDict constructions per query**, and it measured as the
single largest allocator in the process (`TermsDict.<init>` alone = 11.16% of
ALL allocation samples).

The per-hit acquisition existed for a real reason, documented in the code: KNN
hits arrive in SCORE order, `advanceExact` is forward-only, so one shared
iterator would seek backwards. The fix is to satisfy that contract properly
rather than by re-acquiring — resolve the docvalues in **docid order** (one
forward-only iterator per leaf), then emit in the original **score order**.

The result list is identical by construction, not merely by test: same doc set,
same `sd.score`-derived cosines, same selection rule (first k that resolve, in
score order). Work stays O(k) rather than O(fetch) via batching.

Note this is NOT the stored-fields/LZ4 bug of §14.1 and §15 — this class already
used DocValues correctly. It is the adjacent anti-pattern: re-acquiring the
accessor per document instead of per segment.

## What is left (next campaign)

The profile is no longer dominated by any single frame — the remaining top
entries are diffuse:

| % CPU | Frame | Note |
|---|---|---|
| 14.4 | `LuceneHnswChunkVectorIndex.topKChunks` | now mostly inherent HNSW search + the String/UUID decode chain |
| 13.3 | `CryptoUtil.verifySaltedPassword` | residual: cache misses and 60s TTL expiry. Raising the TTL trades staleness for CPU |
| 8.3 + 3.6 + 1.7 | `FrontmatterParser.{parseYaml,split,loadStrict}` | 13.6% combined — frontmatter is still re-parsed more than it is cached |
| 5.4 + 3.4 | `MarkdownParser.{parse,collectLinks}` | render path |

Ranked candidates for a follow-up:
1. **Store chunk UUIDs as raw 16 bytes** in the HNSW index instead of a 36-char
   string, and rebuild via `new UUID(msb, lsb)` — removes `utf8ToString()` +
   `UUID.fromString()` per hit. Index is derived/rebuildable, so no migration.
2. **Frontmatter parse caching** — 13.6% of CPU across three frames suggests the
   `FrontmatterMetadataCache` is being bypassed on some paths, the same class of
   defect as §15 fix #3.
3. **Password verify cache TTL** — a deliberate staleness/CPU tradeoff, an
   operator decision rather than a code fix.
