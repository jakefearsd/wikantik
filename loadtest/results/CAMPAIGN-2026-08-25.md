## Iteration 1 — BasicAuthFilter session fast path was dead code

`BasicAuthFilter` compared the Basic-auth username against
`Session.getUserPrincipal()`, but `WikiSession.injectUserProfilePrincipals()`
sets that to the user's **FullName** (preferring `WikiPrincipal.FULL_NAME`);
the login name lives on `getLoginPrincipal()`. So `"testbot".equals("Test
Automation Bot")` — false on every request, for every user whose full name
differs from their login name. The "don't re-login on every request" guard had
never fired in production.

Fixed by matching either principal. Measured on a session-holding client:
**312 ms -> 1.6 ms** per admin request.

The aggregate profile did NOT move (96.01% still bcrypt), which was the
informative part: the harness — like monitoring pollers, cron jobs, CI scripts
and SDK one-shot calls — is stateless and carries no session cookie, so it
cannot use the fast path at all. That client class is the one that costs money.

## Iteration 2 — short-TTL successful-verification cache

`AbstractUserDatabase.validatePassword` now caches successful verifications,
mirroring `ApiKeyService.verifyCache` (§14.2 of ScalingCharacterization).

- Key: `loginName + ' ' + sha256Hex(password || storedHash)`. Binding the key
  to the stored hash means a password change rotates the key, so it takes
  effect **immediately** rather than after the TTL.
- Successes only — bcrypt's cost is a deliberate brute-force deterrent, so a
  wrong password always pays full price.
- Legacy-hash migration branch excluded (it mutates and saves the profile).
- Kill switch: `wikantik.auth.password.verifyCache.ttlSeconds=0`.
- Cannot bypass lockout: `UserDatabaseLoginModule` checks `profile.isLocked()`
  after and outside `validatePassword()`, against a freshly-fetched profile.

## Iteration 3 — HNSW docvalues acquired per leaf, not per hit

`LuceneHnswChunkVectorIndex.topKChunks` called
`ctx.reader().getSortedDocValues(...)` **twice per hit**. That is not a cheap
accessor — each call constructs a fresh `Lucene90DocValuesProducer$TermsDict`
with its own block buffers. At the shipped `wikantik.bundle.dense.top_k = 300`
that is up to **600 TermsDict constructions per query**, and it measured as the
single largest allocator in the process (`TermsDict.<init>` alone = 11.16% of
ALL allocation samples).

The per-hit acquisition existed for a real reason, documented in the code: KNN
hits arrive in SCORE order, `advanceExact` is forward-only, so one shared
iterator would seek backwards. The fix is to satisfy that contract properly
rather than by re-acquiring — resolve the docvalues in **docid order** (one
forward-only iterator per leaf), then emit in the original **score order**.

The result list is identical by construction, not merely by test: same doc set,
same `sd.score`-derived cosines, same selection rule (first k that resolve, in
score order). Work stays O(k) rather than O(fetch) via batching.

Note this is NOT the stored-fields/LZ4 bug of §14.1 and §15 — this class already
used DocValues correctly. It is the adjacent anti-pattern: re-acquiring the
accessor per document instead of per segment.

## Iteration 4 — `FrontmatterParser.split` copied the whole body to test 4 chars

`split()` tested for the empty-frontmatter case with
`CLOSING_IMMEDIATE.matcher( text.substring( yamlStart ) )`. That `substring`
copied the **entire remaining page body** into a new String on every call, for
every page, purely to check whether `---\n` sat at that offset — then discarded
it. Replaced with `String.startsWith(prefix, offset)`, which allocates nothing.
`CLOSING_IMMEDIATE` was also a byte-identical duplicate of `OPENING` and is gone.
Net: less code.

| | Iter 3 | Iter 4 | Δ |
|---|---|---|---|
| `split()` allocation | 8.50% (1722) | 4.11% (844) | **−51%** |
| `split()` CPU | 3.63% (40) | 2.95% (35) | −13% (within noise) |

Honest reading: the copy was memory **bandwidth**, not compute, so the win lands
in allocation/GC pressure, not on-CPU samples or latency. Total CPU samples went
1102 → 1187 across the two runs — run-to-run variance at these sample counts, not
a regression. Guarded by `FrontmatterParserTest` (empty-block LF + CRLF,
triple-dash-in-body); mutation-checked (a wrong delimiter length fails the suite).

**Gotcha for future work:** `wikantik-main`'s `FrontmatterParserTest` exercises the
*installed* `wikantik-api` jar, not the source tree. Only the `wikantik-api` suite
actually guards that class — mutate-and-test there.

## Considered and deliberately NOT done

**Route `/admin/knowledge-graph/pages-without-frontmatter` through
`FrontmatterMetadataCache`.** `KgMaintenanceAdminHandlers.handleGetPagesWithoutFrontmatter`
does `getAllPages()` + `getPureText()` + `FrontmatterParser.parse()` for the whole
corpus on **every GET**, and only needs `metadata().isEmpty()` — textbook cache
bypass, the same shape as §15 fix #3.

Rejected on cost/benefit: the cache is only reachable via
`engine.getManager(FrontmatterMetadataCache.class)`, and `DecompositionArchTest`
declares "no new `WikiEngine#getManager` callers — services must receive their
dependencies" as a **permanent** rule. The alternative is threading a
`Supplier<FrontmatterMetadataCache>` down through `AdminKnowledgeResource`'s
construction — real cross-layer plumbing. The endpoint is 1 of 10 audit-tier
surfaces (~1% of admin requests). Not worth the architectural churn; revisit only
if the dependency arrives there for another reason.

## Iteration 5 — display-math regex short-circuit

`DisplayMathPreProcessor.transform` ran a DOTALL/MULTILINE backtracking regex over
the whole page body on every parse, including the common case of a page with no
math at all. Added `if ( !source.contains( "$$" ) ) return source;` — output-identical
(no match ⇒ `appendTail` returns `source` verbatim), one line, no new state.

Worth calling out honestly: at 9 samples this is **below the run-to-run noise floor**
(identical configs measured 971–1187 total CPU samples across this campaign), so it
cannot be individually attributed. It is a provably-correct reduction in work, kept
on that basis, not on a measured delta.

## The markdown "render" hotspot is actually the SEARCH path

The largest remaining cluster looked like page rendering. Attributing whole stacks
rather than leaf frames showed otherwise:

| | samples | share |
|---|---|---|
| markdown parse/collectLinks total | 164 | 13.8% of all CPU |
| ...reached via `DefaultLuceneSearcher.findPages` | **157** | **96% of those** |
| ...via `DefaultContextRetrievalService` | 4 | |
| ...page rendering and everything else | 3 | |

`DefaultLuceneSearcher.findPages` calls `pm.getPage()` **per hit** (line ~311).
That routes to `CachingProvider.getPageInfo` → `refreshMetadata`, which does a
FULL extension-laden markdown parse (plus a second bare parse inside
`collectLinks`) to populate page metadata — guarded only by `page.hasMetadata()`,
a flag on the `Page` **instance**. The page-object cache recycles instances on a
60s TTL, so every search re-parses the markdown of every hit it touches.

The search loop only uses the page for its ACL and `lastModified`. It never needs
the parsed metadata.

**Not fixed here, deliberately.** All three of `getPage`/`getPage(v)`/`getPageInfo`
funnel through `refreshMetadata`; there is no metadata-free accessor. Adding one is
a `PageManager` interface change across api → main → repository, and making
metadata materialisation lazy changes `[{SET}]` variable semantics app-wide. That
is a project with its own plan, not a minor edit — the same call the 2026-07-03
tier-1 plan made about the `collectLinks` double-parse. **It is now the single
largest remaining item: ~13% of CPU.**

Also verified already-fixed and still in place (no action needed): flexmark
extensions are `static final` and shared (tier-1 Task 6); `DefaultAclManager`'s
version-keyed `aclCache` (tier-1 Task 3); `isLikelyWikiSyntax` hash memoisation.
No per-call `Pattern.compile` remains anywhere in that cluster.

## Operational lesson — do not run the gate against a live profiling stack

The first `--parallel 4` run after iteration 5 failed two ITs:
`OntologyPublicEndpointsIT` ("public page must appear in the dump") and
`StructuredFrontmatterEditorIT.rawYamlRoundTrip` (Selenium `TimeoutException`).
Neither was a code defect. The deployed Tomcat and the dev ollama on 11434 were
still running and competing with the IT containers, the shared test embedder on
11435, and the Selenide browser — the log shows embedder retry storms and an
"ontology rebuild already RUNNING" race. With the profiling stack stopped and the
SAME code, the rest module passed 254/254 and the full IT phase passed clean, in
**4m30s vs the failing run's 6m01s**. Stop the profiling stack before gating.

## Iteration 6 — the harness was under-measuring the agent surface by 40x

Investigating "the MCP path to search" turned up a harness defect first.

The read mix drove `/wikantik-admin-mcp` with `read_page`, `search_knowledge`
and `query_nodes`. Profiling attributed **0.4% of CPU** to MCP, which looked like
"the agent surface is cheap." It is not — **two of those three tools are no-ops on
this corpus.** `search_knowledge` and `query_nodes` query **Knowledge Graph nodes
only** (pure JDBC against `kg_nodes`, no page store, no retrieval); with no
extracted entities they return `{"results":[]}` in ~3 ms. The tool says so itself:

    "search_knowledge searches Knowledge Graph nodes only; if you expected
     page-body matches, call retrieve_context with the same query."

The real agent retrieval tools live on **`/knowledge-mcp`**, which the harness
never called: `retrieve_context`, `assemble_bundle`, `read_pages`, `get_briefing`.

Measured directly (3 calls each):

| tool | min | avg | max |
|---|---|---|---|
| `retrieve_context` | 9 ms | 607 ms | **1801 ms** |
| `assemble_bundle` | 19 ms | 26 ms | 36 ms |
| `read_pages` | 2 ms | 2 ms | 3 ms |
| `search_knowledge` | 3 ms | 3 ms | 4 ms |

`retrieve_context`'s 9 ms warm vs 1801 ms cold is exactly the `refreshMetadata`
signature: a cold call re-parses the markdown behind every hit; a warm one finds
`hasMetadata()` already set.

`knowledgeAgentFlow` now drives `/knowledge-mcp` (55% `retrieve_context`,
30% `assemble_bundle`, 15% `read_pages`) at 20% of read iterations.

### Corrected attribution

| Frame | broken mix | real mix |
|---|---|---|
| **MCP tool dispatch** | **0.4%** | **16.1%** |
| `ContextRetrievalService` | 31.5% | 33.1% |
| `LuceneHnswChunkVectorIndex.topKChunks` | 10.7% | **21.4%** |
| `CachingProvider.refreshMetadata` | 15.3% | 7.2% |

**A load mix that calls the wrong tool does not under-measure a surface by a
little — it hid 16% of CPU behind an empty result set.** Same lesson as the admin
surface at the start of this campaign, one layer down.

## Answering "is the MCP path to search affected by the markdown re-parse?"

Traced end to end:

| MCP tool | path | hits the per-hit parse? |
|---|---|---|
| `search_knowledge` | `SearchKnowledgeTool` → `KgNodeRepository.queryNodes` — pure JDBC on `kg_nodes` | **No** — never touches the page store |
| `query_nodes` | same | **No** |
| `retrieve_context` | → `ContextRetrievalService` → `SearchManager.findPages` → `DefaultLuceneSearcher.findPages` | **Yes** — same bottleneck as `/api/search` |
| `read_page` / `read_pages` | `pm.getPage()` per slug (`getPureText()` does NOT re-trigger it) | **Yes** — exactly one parse per page |

So the *KG* search tools are clean; the *retrieval* tool shares `/api/search`'s
bottleneck. A fix at `findPages` covers both surfaces.

`/api/search` actually pays it **twice**: once per hit inside `findPages`
(`DefaultLuceneSearcher.java:311`), and again in
`DefaultAuthorizationManager.filterViewable` (`:188`), which loops
`pageManager().getPage(name)` per result — batch in call-shape only.

### The parse is dead weight for these callers — verified

- **ACL** does not need it: `DefaultAclManager.getPermissions` uses its own
  `(name, version, lastModified)`-keyed cache, and on a miss reads `getPureText()`
  + a regex scan for `[{ALLOW}]`. No flexmark.
- **Recency** uses `page.getLastModified()` — a provider-native field.
- **Retrieval metadata shaping** goes through `FrontmatterMetadataCache`, not
  `page.getAttribute()`.
- The only consumer of the attributes this parse populates is **page rendering**
  (`WikiContext` ALIAS/REDIRECT, `DefaultVariableManager` `$var` substitution) —
  and, at index time, `DefaultLuceneIndexer:509` reading `keywords`. **The indexer
  genuinely needs it and must keep it.** Nothing on the search path reads them.
