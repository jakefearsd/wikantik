# Profiling campaign 2026-09-25 — first run on a production-shaped remote host

Status: **setup + bring-up complete; baseline profile running.** Results sections
below are filled in as each iteration lands.

## What is different about this campaign

Every prior arc (ScalingCharacterization §9–§17) ran against a **local bare-metal
Tomcat with k6 co-resident**, so absolute RPS was k6-confounded and only CPU
composition and p95 were trustworthy. This campaign changes three things at once
— deliberately, because all three are environment, not code:

| | Prior campaigns | This campaign |
|---|---|---|
| Target | local bare-metal Tomcat, 10–16 cores, unbounded | **docker2** container, **2 GB limit**, G1, `MaxHeapSize≈1.43 GB` (`MaxRAMPercentage=70`) — same shape as prod |
| Load generator | **co-resident with the target** | **separate host** (workstation 192.168.0.4 → docker2 192.168.0.5, 0.45 ms RTT) |
| Corpus | 1201 pages / **1635 chunks** | 1202 pages / **18,792 chunks / 18,792 embeddings** (dim 1024) — **11.5× the chunks**, 85% of prod's 22,001 |
| Embedder | local CPU ollama | **GPU inference host** (`inference.jakefear.com:11434`), warm embed 14–49 ms |

Load generation being off-box is the methodological fix: RPS is now a real number
rather than a number the load generator was stealing CPU from.

### Environment detail

- Host docker2 (`cicd`, 192.168.0.5): Ryzen 7 5800U, 8c/16t, 30 GB RAM. Idle at
  bring-up (load 0.09, 98.9% idle) — the co-resident jakemon and CrafterCMS
  stacks are resident but not burning CPU.
- Stack: `docker-compose.yml` + `docker-compose.prod.yml` + a perf overlay,
  project `wikantik-perf`, app on 18080. DB `pgvector/pgvector:pg18`, 2 GB,
  `shared_buffers=256MB work_mem=32MB` — prod's settings.
- Perf knobs **identical to prod** (`.env.prod`): `WIKANTIK_DENSE_BACKEND=lucene-hnsw`,
  `DENSE_EF_SEARCH=100`, `LUCENE_DIRECTORY=nio`, `VERSIONING_CACHE_SIZE=5000`,
  `MAX_INFLIGHT_REQUESTS=390`, `GENAI_MODE=full`.
- Deliberate divergences from prod: embeddings point at the **inference host**
  rather than prod's in-stack CPU sidecar (the point of the exercise); SSO /
  IndexNow / SMTP / backup sidecar omitted; a freshly generated DB password.
- **No production data was copied.** The corpus is the repo's version-controlled
  `docs/wikantik-pages/` tree, chunked and embedded on-host. Prod's DB carries
  real user accounts and emails; exporting it was neither necessary nor
  appropriate for a profiling target.

## Defects found during bring-up (before a single profile was taken)

### 1. The harness could only ever get 501 from the tools surface — FIXED

`loadtest/lib/endpoints.js` `toolsCall()` drove `GET /tools/search_wiki?q=…`.
`ToolsOpenApiServlet` routes `search_wiki` in **`doPost` only** — `doGet` serves
`/openapi.json` and `/page/*`, then falls through to `writeNotImplemented()`
(`ToolsOpenApiServlet.java:103-116, 253`). So every tools call in every run
returned **501**, which is a 5xx and is **not** covered by that surface's
`responseCallback` (200–499) — it inflated `http_req_failed` and profiled an
error path instead of the tool.

Fixed to `POST` with the real contract (`{"query","maxResults"}`, read via
`readJsonBody`). This is the same class of defect as the 2026-08-25 campaign's
iteration 6 (harness driving KG-node tools that were no-ops on the corpus): **a
load mix that calls a surface the wrong way does not under-measure it, it
measures something else entirely.**

### 2. Dense retrieval was dark despite 18,792 embedding rows committed

After `POST /admin/content/rebuild-indexes` completed (`state=IDLE`,
`chunks_written=18792`, `embeddings_indexed=18792`), `/api/bundle` still answered
in 2.8 ms with `topSimilarity: -1.0`, `confidence: unknown`, **0 sections**.

Cause is the documented `lucene-hnsw` reload requirement: only `pgvector` reads
through to the DB; `lucene-hnsw` builds a **separate in-process index** that was
loaded at startup with `rows=0`, and the reload hook fires from
`BootstrapEmbeddingIndexer.invokePostRun()` **on the success path only** — the
bootstrap had already recorded `SKIPPED_NO_CHUNKS` at startup (there were no
chunks yet). A restart fixed it: `Lucene HNSW index loaded: rows=18792 dim=1024`,
`bm25 chunks=18792`, and the bundle then returned `topSimilarity 0.5915 /
confidence strong / 12 sections`.

**Operational consequence:** on a `lucene-hnsw` deployment, a rebuild that
populates chunks for the first time leaves hybrid silently BM25-only until the
next restart or successful bootstrap. `topSimilarity: -1.0` with
`confidence: unknown` is the tell.

### 3. The rate limiter has never been exercised by any load test — by construction

`RateLimitFilter` puts `/api/bundle`, `/api/search` and `/sparql` in an
"expensive" tier: **3 req/s per client, 10 req/s global**, keyed on
`getRemoteAddr()`, with **loopback always exempt**
(`RateLimitFilter.java:99-105, 236-237, 286-293`).

Every prior campaign ran k6 **on loopback**, so this filter was exempt in all of
them and has never appeared in any measurement. Driving from a remote host
exposes it immediately.

Measured, production-realistic, from a remote client:

| | result |
|---|---|
| 20 sequential `/api/search` from 192.168.0.4 | **200 = 3, 429 = 17** |

That is the genuine behaviour a remote API consumer sees today. For profiling it
had to be neutralised, or the run would measure the rejection path: the driver
host is exempted via `WIKANTIK_RATELIMIT_EXEMPT_CIDRS`, after which 30/30
searches pass. This **restores parity with prior campaigns' loopback exemption**
rather than weakening a control.

A secondary observation: behind Docker's published-port NAT the app did not
observe `192.168.0.4`, so a `/32` exemption did not match and the bridge range
had to be exempted instead. In this stack the per-client limiter therefore cannot
distinguish external clients at all. Prod is not affected — it sits behind
Cloudflare with `RemoteIpValve` + `CF-Connecting-IP` — but it means a
reverse-proxied deployment without that valve configured would rate-limit all
clients as one.

## Hotspot #1 — `topKChunks` is a vector-READ problem, not a vector-MATH problem

Splitting the frame by phase and caller (the §17 method) rather than trusting its rank:

| | |
|---|---|
| Share of all CPU | **36.77%** (606 samples) |
| Called by | **`DenseRetriever.retrieveWithChunks` 75.25%**, `ContributingChunkAssembler` 15.18%, `HybridChunkSectionSource` 9.57% |
| Phase | `IndexSearcher.search` **95.05%**, `resolveBatch` 4.46% |
| Leaves | **`ByteBuffersDataInput.readFloats` 58.25%**, `PanamaVectorUtilSupport.cosineBody` 13.70%, `readGroupVInts` 5.78%, `getFloatBuffer` 3.80% |

**~4.25× more CPU goes into reading float32 vectors than into the cosine math they
feed.** The index is `KnnFloatVectorField` + `Lucene99HnswVectorsFormat` — raw
float32, so a 1024-dim vector is a **4 KB read for every candidate the graph
visits**, and the dominant caller requests `k=500`.

Two incidental findings from the same data:

- `resolveBatch` is only 4.46% of the frame, so the iteration-3 (docvalues per leaf)
  and iteration-8 (UUID → two `NumericDocValues` longs) fixes **are holding**. There
  is nothing left to win there.
- **`ef_search` is inert.** The query fetches `Math.max(k, efSearch)`, and every
  caller asks for k ≥ 300 (`bundle.dense.top_k`=300, `hybrid.dense.chunk-top`=500)
  against `ef_search`=100 — so the configured knob can never bind. Documented in
  `ini/wikantik.properties` rather than silently left misleading.

### Fix: opt-in scalar quantization

`wikantik.search.dense.lucene.quantization` = `none` (default, unchanged behaviour)
| `seven_bit` | `unsigned_byte` | `packed_nibble`, mapped to Lucene 10.5.1's
`Lucene104HnswScalarQuantizedVectorsFormat`. Only the codec changes — the field stays
`KnnFloatVectorField` — and the index is rebuilt from `content_chunk_embeddings` on
boot, so there is **no migration**. Unrecognised values fall back to `none` (fail
safe: a typo must not take dense retrieval offline). `HnswParams` gained a 3-arg
convenience constructor so all ~12 existing call sites compile unchanged.

Guards: `HnswParamsTest` (+4) and a new
`LuceneHnswChunkVectorIndexTest.quantizedIndexStillRanksNearestFirstAndMapsPages`
that pins ordering and id→page mapping under quantization at a realistic dimension
(64, not 3 — quantization pads/packs dimensions). 18/18 green.

**Recall guard:** a `lucene-hnsw-q7` backend was added to
`RetrievalQualitySmokeTest$ParityGate` plus
`inmemory_and_quantized_hnsw_within_recall_epsilon`; the gate runs 8/8 green, so 7-bit
quantization recalls within **nDCG@5 ≤ 0.02** of brute force on that corpus.

**What that evidence is and is not.** The gate's corpus is three pages / three chunks
with deterministic query vectors — it catches gross breakage (broken codec, permuted
results, dimension mismatch) and nothing subtler, because with three documents
quantization error cannot plausibly reorder them. It is **not** grounds to flip the
default: that needs the `eval/bundle-corpus` harness against the full ~19k-chunk index.
The shipped default therefore stays `none`.

## Hotspot #2 — 88% of `refreshMetadata` is ACL gating that needs no metadata

| | |
|---|---|
| Share of all CPU | **13.65%** (`MarkdownParser.parse` 12.44%, 99.5% of it via `refreshMetadata`; `collectLinks` a **second** flexmark parse) |
| Reached from | **`RestServletBase.checkPagePermission` 60.00%**, knowledge-MCP guest view gate 15.11%, `WikiPageFormatFilter.doFilter` 13.33%, genuine retrieval ~11% |

All three ACL entry points funnel through **one line** —
`PermissionFilter.permissionFor()` calling `pages().getPage(pageName)`, which routes
through `CachingProvider.refreshMetadata` and runs two full flexmark parses to
populate `[{SET}]` variables. The system was parsing markdown to answer *"may this
user view this page?"*.

The §16 campaign deferred this as needing "a `PageManager` interface change… a
project with its own plan". That interface change **already shipped** (for search
hits), so the fix is now one line.

**Why it is safe — verified, not inferred:**

- `DefaultAclManager.getPermissions` resolves inline `[{ALLOW …}]` ACLs itself: it
  reads `getPureText(page)` and calls `parseAcl`, behind its own
  version+lastModified-keyed cache. It never depends on `refreshMetadata`.
- `PermissionFactory.getPagePermission` reads only `page.getWiki()` and
  `page.getName()`.
- **`DefaultAuthorizationManager.filterViewable` already does exactly this** on the
  batch path — `getPageWithoutMetadata` → `aclManager().getPermissions` →
  `PermissionFactory`. The single-page path was simply never migrated; the two are
  now consistent.
- The chain is overridden end-to-end (`DefaultPageManager` → `DefaultPageRepository`
  → `CachingProvider.getPageInfoNoMetadata`), so the change is not a silent no-op.

Also applied to `WikiPageFormatFilter` (its own `getPage`), which uses only
`getName()` and `getLastModified()`.

Guards: new `PermissionFilterTest.permissionCheckMustNotForceMetadataParse` (red
first: *"Wanted but not invoked: getPageWithoutMetadata"*), the five existing stubs
migrated so they keep covering the page-exists branch instead of silently going
vacuous, and `batchViewabilityMatchesPerPageChecks`, which stands up a real
`TestEngine` with an actual `[{ALLOW view Admin}]` page and compares anonymous vs
admin decisions. 9/9 green.

## Run-integrity incident — and what it says about the tooling

Two consecutive iteration-1 runs were killed mid-flight by the agent harness with
"system is running low on memory". The first died during k6 startup (87 s window,
24 CPU samples — useless). The second died at **1m52 of 3m, 5,536 iterations, 0
interrupted**.

**The machine was never out of memory.** Checked after the second kill: no kernel
OOM records in `dmesg`, no cgroup limit (`memory.max = max`), PSI memory pressure
flat at `some avg10=0.00 / full avg10=0.00`, swap essentially untouched (1.6 MB of
8 GB), 43 of 61 GB available. The kill is the *harness's* low-memory heuristic firing
on a long-running background task — most plausibly counting 33 GB of page cache as
unavailable — not genuine exhaustion.

Two things came out of it, and it is worth keeping them apart:

1. **A real latent defect, fixed.** `bin/lib/jfr-cpu-report.py` ran `jfr print` under
   `subprocess.run(capture_output=True)`, holding the entire expansion of a recording
   in one Python string — at `--stack-depth 40` an allocation pass over ~23k events is
   hundreds of MB, and it lands at the *end* of a profiling run. It now streams
   line-by-line, so memory is bounded by one line regardless of recording size.
   Verified by re-reducing the baseline recording: identical totals (1,648 / 22,944 /
   17) and **byte-identical output tables**, peak RSS 878 MB. This was worth fixing on
   its own merits, but it was **not** the cause of the kills.
2. **A methodology change.** A 6-minute profiling run must not be one long background
   task. Decompose it: start the JFR via the admin endpoint, run k6, stop + download,
   reduce — each step short and independently retryable. `bin/profile-iteration.sh`
   does all four in one invocation, which is convenient and fragile.

**Operational gotcha worth remembering:** `JfrProfilingService` permits exactly one
concurrent recording, so a killed run leaves a `RUNNING` orphan that makes the next
`start` throw. Both kills left one. Stopping the orphan reconciles it to `FINISHED` —
and in the second case that recovered a **genuinely usable 7.23 MB recording with
1,039 ExecutionSamples** taken under full 40+10 VU load. Check
`/admin/profiling/jfr/recordings` before retrying, and salvage rather than discard.

## Iteration 1 — the fix did nothing, and the measurement is what caught it

Composition from a salvaged 206 s window (1,039 ExecutionSamples) under the identical
40 read + 10 admin VU mix. Valid for CPU **shares** — this methodology's primary
signal — but carrying no RPS/latency aggregate, because k6 was killed before its
end-of-test summary.

| | baseline | iteration 1 |
|---|---|---|
| `refreshMetadata` share of CPU | 13.65% | **13.19%** |
| …reached via `checkPagePermission` | 60.00% | **62.04%** |
| …via `WikiPageFormatFilter` | 13.33% | 12.41% |
| …via knowledge-MCP guest gate | 15.11% | 12.41% |
| `topKChunks` | 36.77% | 38.40% (quantization still off, as expected) |

**Unchanged.** And the deployed jars genuinely contained the change — verified by
grepping the shipped class constant pools: `PermissionFilter` and
`WikiPageFormatFilter` both reference `getPageWithoutMetadata`, and
`HnswParams$Quantization` is present. The code shipped and did nothing.

### Root cause: I fixed the wrong line

Dumping the **full** caller chain rather than the first-REST-frame summary:

```
refreshMetadata ← CachingProvider.getPageInfo ← DefaultPageRepository.getPageInfo
  ← …getPage ← DefaultPageManager.getPage
  ← DefaultAuthorizationManager.decide          ←—— the actual caller
  ← DefaultAuthorizationManager.checkPermission ← PermissionFilter.canAccess
```

`decide()` performs its **own** `getPage` *after* `PermissionFilter` has already
loaded the page metadata-free. Removing one of two loads changes nothing. Summing the
chains through `decide`: 74.45% (`canAccess`) + 12.41% (`canAccessQuietly`) + 2.92%
(`findPages`) ≈ **90% of all `refreshMetadata`** — including the search path, which
had already been migrated to the metadata-free accessor in an earlier campaign only
for `decide` to undo it on the next call.

`filterViewable` in that same class already used `getPageWithoutMetadata` (line 191)
with *identical* downstream usage — `aclManager().getPermissions(page)` then
`PermissionFactory` — so `decide` (line 233) was simply the un-migrated sibling. That
made the correct fix provable by comparison **inside one file** rather than by
inference.

### The test that lied

The first guard, `PermissionFilterTest.permissionCheckMustNotForceMetadataParse`,
**passed while the system kept parsing on every request.** It asserted that
*`PermissionFilter`'s own call site* had changed — not that no parse occurs on the
authorization path. It was a true statement about the wrong thing, and it produced
false confidence in a fix worth zero.

The replacement guard,
`DefaultAuthorizationManagerCITest.pagePermissionDecisionMustNotForceMetadataParse`,
asserts at the layer that actually loads the page, and its red output names the
culprit outright: *"However, there was exactly 1 interaction with this mock:
`pageManager.getPage("GuardedPage")`"*.

**Lesson, and it generalises past this bug:** assert the *property you care about*
(no metadata parse on this path) at the layer that can violate it — not that one
call site you happened to edit now reads differently. A frame-level fix verified by a
frame-level test will agree with itself and still be wrong. Only the profile caught
it.

### …and the inverse failure, the same day

The `doGet` guard then failed for the opposite reason: it went red while the fix was
**already working**. `engine.saveText()` parses the page as a side effect, so the
cached instance carried metadata before the GET ever ran — the test was asserting on
its own setup.

Adding an explicit precondition assertion separated the two causes in a single run
(`PRECONDITION: saveText must not have parsed the page before the GET runs ==>
expected: <false> but was: <true>`). The fix is `Page.clearHasMetadata()`, which
resets only the flag while preserving attributes and the ACL.

The sibling guard was worse: because `saveText` had already set the flag, its
`assertTrue(hasMetadata())` for `?render=true` passed **without render=true doing
anything at all** — a green, vacuous test. Both guards now clear the flag first.

**Two failure modes, one root cause:** a test whose subject overlaps its own fixture
proves nothing in either direction. The first version passed while the system was
broken; the second failed while the system was fixed; the third was green and
vacuous. State the precondition explicitly and the ambiguity disappears.

### Fixes applied after this finding

| Site | Share of `refreshMetadata` | Page used for |
|---|---|---|
| `DefaultAuthorizationManager.decide:233` | **~90%** | `getPermissions` → `decideByAcl` only |
| `BundleServiceWiring.versionOf` | 4.4% | `p.getVersion()` only |
| `DefaultContextRetrievalService` rerank fill-in | 2.9% | wrapped in identity-only `DenseOnlySearchResult` |

Deliberately **not** changed: `DefaultContextRetrievalService.getPage(String)` (backs
`RetrievedPage`) and the `"Main"` anchor lookup. Neither appeared in the hot
attribution, and changing code the profile did not implicate buys risk without
measured benefit.

Guards: 59/59 green across `DefaultAuthorizationManagerCITest` (incl. the new guard),
`PermissionFilterTest`, `SearchPermissionTest` and `AuthorizationManagerTest`, with
the five pre-existing `getPage` stubs migrated so they keep covering the ACL branch
instead of silently going vacuous.

### Honest reading of the 13.65% → 10.57%

The win is ~3.1 points of total CPU (a 23% cut to that frame), not the full 13.65% —
and the reason is the one **registered in advance**, before iteration 1 was run: on
`/api/pages/{slug}` the parse does not disappear, it **relocates** to `doGet`'s own
`pm.getPage`. Previously `checkPagePermission` parsed first and set `hasMetadata`, so
`doGet`'s later fetch was a cache hit — one parse per request either way. The genuine
savings are the paths that check permission and then never load the page.

That prediction was briefly contradicted by iteration 1 (where the wrong line was
fixed and nothing moved) and is now confirmed: the residual is 99.41% `doGet`.

**Left deliberately unfixed.** Making `doGet` metadata-free needs conditional logic:
with `?render=true` it builds `Wiki.context().create(engine, request, page)` and calls
`textToHTML`, and rendering may legitimately consult the `[{SET}]` variables
`refreshMetadata` populates. The profiled mix never sets `render=true`, but changing
production behaviour on the strength of what the load mix happens to exercise is
exactly the mistake this campaign is documenting. It is the ranked next step, with its
own tests — not a bolt-on.

Throughput and percentiles are flat by design: at 40 VUs this box is not
CPU-saturated, so removing work buys **headroom**, not speed (the §17 precedent). The
failure-rate drop 0.40% → 0.27% is the tools GET→POST harness fix, not a server
change.

## Measuring recall, not just CPU

From iteration 4 onward the remaining levers are **retrieval tuning**, where CPU falls
almost by construction and the only question that matters is what it costs in quality.
There was no existing way to measure that against a live instance: `bin/search-eval/`
is empty, `run-experiment-local.sh` drives embedding experiments against the local DB,
and `POST /admin/retrieval-quality/run` needs a seeded `query_set_id`.

So the campaign uses `eval/bundle-corpus/queries.csv` — which already carries a
`gold_canonical_id` per query — probed against live `/api/bundle`, scoring the share
of queries whose **gold page appears in the returned sections**. That is a real
section-level recall signal rather than a similarity proxy.

**Control (chunk-top=500, iteration-3 build):**

| | |
|---|---|
| queries | 39 (0 errors, 0 dense-dead) |

## Iteration 4 — dense fan-out `chunk-top` 500 → 200: measured, rejected

### A probe that scored 0% — and why that was the probe, not the system

The first `/api/search` recall probe returned **0/37**, which is not credible against a
corpus the bundle hits 92.3% of. Two compounding faults, both mine:

1. It scored `/api/bundle`, which is governed by `wikantik.bundle.dense.top_k` via
   `DenseChunkSectionSource` — **not** by `hybrid.dense.chunk-top`, which feeds
   `DenseRetriever` → `/api/search` and `retrieve_context`. The identical
   0-lost/0-gained bundle result was structurally guaranteed: the probe could not see
   the variable being changed.
2. The `/api/search` probe then built its canonical-id → page-name map by scavenging
   bundle sections, whose `pageName` field is **null**, so every gold lookup missed.

Both fixed by using `page_canonical_ids.current_slug` (68/68 gold ids resolve) and the
verified response shape `{"query","results":[{"name"}],"total"}`. Sanity check that
caught it: for `q01` the gold page `BuildingAndDeployingLocally` ranks **#1**.

**Lesson:** before trusting a null result, prove the probe can observe the variable.
An A/B that returns *byte-identical* output is evidence of a blind instrument, not of
a free change.

## Iteration 5 — the admin dashboard re-scans the corpus on every poll

With `refreshMetadata` gone, the `FrontmatterParser` cluster became the largest
*application* cost at ~10.4% of CPU (`parseYaml` 6.65%, `split` 3.70%). Attributing it
by entry point shows it is not diffuse — it is three admin endpoints sharing one
defect:

| Entry point | share of `parseYaml` | share of `split` |
|---|---:|---:|
| **`AdminDerivedResource`** (`/admin/derived/status`) | **60.8%** | **40.7%** |
| `KgMaintenanceAdminHandlers` (`pages-without-frontmatter`) | 20.6% | 20.4% |
| `AdminFrontmatterIssuesResource` (`parseStrict`) | — | 20.4% |
| `PageResource.doGet` | 17.5% | 18.5% |

`GET /admin/derived/status` returns **three integers**, but computes them by streaming
every page name through `getPureText` + a full YAML parse. It is in the dashboard
polling tier, and `buildReflowService()` is constructed *per request* at both call
sites with no caching anywhere in the class.

**The sharpest part: the answer is a constant.** This corpus reports
`derivedTotal: 0`, and so does production — `connector_synced_item` and
`connector_sync_run` are both 0 on docker1. So ~5-6% of all CPU is spent YAML-parsing
~1,200 pages, on every poll, to discover there is nothing to report.

### What was considered and rejected

- **Filter via the structural index.** `PageDescriptor` already carries a `derived`
  flag (`DefaultStructuralIndexService:290`, from `fm.get("derived_from") != null`),
  but `StructuralFilter` exposes only type/cluster/tags/updatedSince/limit/cursor —
  there is no derived predicate, so `listPagesByFilter` cannot select them. Adding one
  is an API change that ripples into the MCP tool surface.
- **Even with it, `staleCount` still needs per-page reads**: it reads
  `derived_extractor_version`, which `PageDescriptor` does not carry. The index could
  supply the *set*, never the versions.
- **A Caffeine cache.** Caffeine is in the root pom's dependencyManagement but is not a
  dependency of `wikantik-rest` and is used nowhere in it. A new module dependency for
  one 3-integer value is not justified.

### Fix

A `volatile` snapshot of `ReflowStatus` behind `wikantik.admin.derived.statusCacheTTL`
(default 30s, `<= 0` disables, unparseable values fail *safe* to 30s rather than
silently restoring the scan), dropped immediately on any reflow so an operator action
is never reported stale. Service construction moved inside the miss branch, since that
was per-request work too.

`staleCount()` — the standalone scanner — was left alone deliberately: its only
production reference is the `ReflowStatus` record accessor, not the scanning method, so
it is not on any hot path. Changing code the profile does not implicate buys risk for
nothing.

Guards: `repeatedStatusPollsMustNotRescanTheCorpus` (three polls, one `status()` call)
and `reflowInvalidatesTheCachedStatus` (poll → reflow → poll re-scans). Both assert on
the mock the existing `Stub` already returns from `buildReflowService()`, so a passing
memoisation check cannot be a fixture artefact — the trap that produced two misleading
guards earlier in this campaign.

**Honest scope note:** on a corpus *with* derived pages the win is smaller, because the
scan then does real work. It is large here and on production only because both report
zero derived pages.

### Iteration 6 fix

Same TTL-memo shape as iteration 5, with two differences that mattered:

- **The scan result is cached, not the response.** This endpoint paginates
  (`limit`/`offset`), so caching rendered JSON would break pagination. The cached value
  is the sorted `List<Map<String,Object>>`; each request paginates from it.
- **The memo lives on the handler, not the servlet.** Unlike
  `AdminDerivedResource.buildReflowService()` (per-request), `KgMaintenanceAdminHandlers`
  is constructed inside `buildRoutes()`, which `routes()` caches in a `transient` field —
  so the handler instance survives requests and a field on it is stable.

Config: `wikantik.admin.kg.pagesWithoutFrontmatterCacheTTL` (default 30s, `<= 0`
disables, unparseable falls back rather than silently restoring the scan).

**What the memo actually saves.** `getAllPages()` is cached (live TTL is **60s** in
containers — `docker/entrypoint.sh` hardcodes it, overriding the 300s ini default) and
page text is cached too. So this is **not** an I/O saving: it is purely the ~1,200
SnakeYAML parses per request. Pre-fix live cost: **0.351 s cold, ~0.037-0.042 s warm**,
returning a single-element list (`total: 1` — only `News` lacks frontmatter).

**The guard counts real work, not cache state.** A delegating `PageManager` installed
via `setManager` tallies actual `getAllPages()` invocations across three polls
(`PageManager` is in `SNAPSHOT_REBUILDERS`, so the hot swap is visible through
`getSubsystems().page().pages()`; `AttachmentResourceTest` is the precedent, including
`@AfterEach` restoration so the counting mock cannot leak into sibling tests). Red
first at `expected: <1> but was: <3>`. Asserting a cache field instead would have been
vacuous — the failure mode that produced three misleading guards earlier in this run.

## A pre-existing flake the gate surfaced (not caused by this work)

`SearchManagerTest.testSimpleSearch3` failed once under `-T 1C`:
`empty results ==> expected: <0> but was: <1>`. Investigated rather than retried,
because "probably flaky" is how a real regression ships.

| Evidence | Result |
|---|---|
| 4× sequential re-runs (`forkCount=1`) | **8/8 green every time** |
| `-T 1C` whole-module re-run | **BUILD SUCCESS**, the test passed |
| Could this work reach it? | No — the only `wikantik-main` changes since the green `fixbuild6` are authz/bundle/HNSW files that passed there, plus one additive `ini` key; the test reads `TestEngine.getTestProperties()` and asserts nothing about properties |

**Mechanism: established facts, and what is still open.** I published a wrong root
cause first and am correcting it here rather than leaving it.

*Ruled out — the page store IS isolated per test.* `setUp()` redirects both
`wikantik.workDir` and `wikantik.fileSystemProvider.pageDir`, and `TestEngine` routes
them through `cleanNewDirFrom(dir, millis)`, which embeds
`getTestEngineCreationOrigin()` — a stack walk yielding `ClassName-methodName`. So each
test method gets `target/<millis>-com.wikantik.search.SearchManagerTest-setUp-<dir>`.
Two theories die on that evidence:

1. *"Classes sharing a fork race on one page store"* — impossible, the class name is in
   the path.
2. *"Millisecond collision between parallel forks"* — would additionally require the
   same class **and** method in the same millisecond.

*Established.* The failure is intermittent (1 occurrence, then 8/8 green across four
sequential runs and a clean `-T 1C` whole-module re-run), the assertion is correct
(a search for overwritten text must return zero), and it is provably unrelated to this
campaign's changes.

*Open.* Since the filesystem is isolated, the surviving suspects are JVM-level: a stale
Lucene index or static cache persisting inside a reused fork (`reuseForks=true`), or a
timing race in asynchronous indexing (the test sets `indexdelay=0`/`initialdelay=0` and
polls with `Awaitility`). Recorded as **open**, not concluded — a third guessed
mechanism would be worth less than an honest unknown.

**Not "fixed" by weakening the assertion.** The assertion is correct — a search for
overwritten text must return nothing. The real repair is per-test fixture isolation
(unique page names, or a private page dir per engine), which is a test-hygiene change
outside this campaign's scope and is recorded here so it is not rediscovered a fourth
time.

After iteration 6 I re-ran the **identical binary, identical config, nothing changed**.

**Three runs of the same binary span 129.6–143.6 samples/1k-req (10.8% peak-to-peak)
and 39.71–47.01% on a single frame's share (7.3pp).** Iteration 6's 143.6 is the
outlier of the three; the configuration's centre is ~130–134. Offered load does not
explain any of it: requests varied only 1.3% across the whole campaign
(10,048 / 9,996 / 10,065 / 9,982 / 9,933 / 10,034), and the spread survives

### What this invalidates — stated plainly

I published cumulative CPU reductions as point estimates. Against a measured noise
floor of roughly **±10% on sample counts** and **±7pp on a frame's share**, those were
overclaimed:

| Claim as published | Status |
|---|---|
| iter 3: "on-CPU samples −14.4%" | **Overstated** — inside the noise band |
| iter 5: "1,385, lowest of the campaign, −16.0% cumulative" | **Overstated** — the same config later produced 1,287 |
| iter 4 "no benefit", iter 6 "below the noise floor" | Correct as written |

### What survives, and why

Structural results are unaffected by sampling noise, because they are not counts of
samples — they are *the disappearance of a code path*:

- **`refreshMetadata` 13.65% → 0.00%.** A frame reaching literally zero across three
  consecutive runs cannot be produced by noise, and the entry-point attribution shows
  the ACL callers (`checkPagePermission` 60%, MCP guest gate 15%,
  `WikiPageFormatFilter` 13%) vanishing outright.
- **Endpoint latency**, measured directly rather than sampled: derived-status
  ~48 ms → ~5 ms; pages-without-frontmatter ~40 ms → ~5 ms.
- **Attribution shifts**: `AdminDerivedResource` 60.8% → 12.5% of `parseYaml`;
  `pagesWithoutFrontmatter` 46.4% → 17.8%.

### The defensible cumulative claim

Load-normalised, baseline sits **outside the entire post-fix range**:

| | samples/1k-req |
|---|---:|
| baseline | **164.0** |
| iter 3 / 5 / 6 | 141.2 / 137.6 / 143.6 |
| final config, 3 runs | 143.6 / 129.6 / 130.1 (centre ~130–134) |

## Judgement — stop tuning here

Three independent levers on the dominant remaining frame are dead, each with a
*mechanism*, not merely a null measurement:

1. **Scalar quantization** — `Lucene104ScalarQuantizedVectorsFormat` retains raw float32
   alongside the quantized vectors for exact rescoring, so `readFloats` never goes away.
2. **`chunk-top` 500 → 200** — inert in cost *and* recall (0 lost / 0 gained / 0 rank
   changed).
3. **`ef_search`** — *structurally* cannot bind: `fetch = Math.max(k, efSearch)`
   (`LuceneHnswChunkVectorIndex.java:325`) and every caller asks k ≥ 300 against a
   configured 100. This also corrects iteration 4's loose phrasing that cost "scales
   with `ef_search`" — the effective fetch is `k`, and iteration 4 already showed
   cutting `k` changes nothing either. The cost tracks neither knob.

Further tuning would also be working below the instrument: ±10% on totals and far worse
per-frame, as the `SessionEventDispatcher` false positive above demonstrates.

**The system was never latency-bound at this load** — p95 moved −4.7% and the failure
rate is flat. The saving converts to **headroom and capacity**, not user-visible speed;
users feel the −21.6% median.

If the remaining 43% is ever worth attacking, it is **not a profiling task**. It is
reading 18,792 × 1024 float32 values, and the only real lever is dimensionality — a
smaller embedding model, or Matryoshka truncation to 256/512 dims — which spends recall
to buy CPU and must be budgeted against the gold-scored probe. That is a
retrieval-quality experiment. Note also that the 43% is weighted by this harness's 40/10
read/admin VU mix; if production searches less than that, it is overstated.
