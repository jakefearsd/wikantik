# Profiling run 2026-10-22: 2.4.59 vs 2.4.60, local A/B

Question: what did 2.4.60 cost? The release added section deep links to context bundles
(`BundleSection.url`), resolved per bundle by reading and parsing each kept page.

## Environment and method

- **Target:** local bare-metal Tomcat 11 on the workstation, with k6 co-resident. docker2, the
  production-shaped host of the 2026-09-25 campaign, was unreachable, so absolute RPS is
  k6-confounded. Only the A/B deltas and CPU composition are trustworthy.
- **Corpus:** 1,180 pages and 18,627 chunks, all embedded (`qwen3-embedding:0.6b`, local CPU
  ollama on 11434). The 2026-09-25 campaign had 18,792 chunks.
- **Binaries:** WARs built from the tags `v2.4.59` (A) and `v2.4.60` (B) in clean worktrees. No
  migrations differ between them, so they share one database.
- **One iteration:** stop Tomcat, swap the WAR, start it, wait until a bundle shows live dense
  retrieval, then the documented 2-minute `smoke` warm-up, then `bin/profile-iteration.sh <label>`
  (3 min, 40 read and 10 admin VUs, JFR). The order was interleaved: A1, B1, A2, B2.
- **Version check per run:** bundle sections carry `url` on B and not on A.
- **Run validity:** request failures were 0.58–0.89% in every run, with zero MCP 401s.

A1 is an outlier. It was the first run on a freshly restarted machine, with a cold page cache for
the index files and the CPU embedder warming up. Without A1, total CPU per request is flat within
the noise floor. **Total CPU hides this release's cost; the stack attribution below shows it.**

## Finding 1: bundle link resolution re-parses every kept page on every bundle

Whole-stack share of all CPU samples (any frame on the stack):

| | A1 | A2 | B1 | B2 |
|---|---:|---:|---:|---:|
| `DefaultBundleAssemblyService.assemble` | 7.09% | 7.24% | 13.33% | 11.17% |
| `DefaultBundleAssemblyService.citeAndDedup` | 0.41% | 0.13% | 6.70% | 4.52% |
| `BundleServiceWiring.sectionAnchors` (new) | — | — | 6.04% | 4.12% |

- Bundle assembly costs **≈1.6–1.8×** the CPU it did in 2.4.59.
- Link resolution is **≈40% of bundle-assembly CPU**: 92 of 203 samples in B1, 62 of 168 in B2.

Inside `sectionAnchors`:
- **75–79%** is flexmark `Parser.parse` of the whole page body, via `SectionAnchors.byHeadingPath`.
- **8–13%** is `FrontmatterParser.parse`, a SnakeYAML parse done only to strip the frontmatter.
- **0%** is `getPureText`, because page text is cached.

Bundle latency, measured sequentially over `/api/bundle`: 20 fixed queries, each instance freshly
deployed, 100 warm-up requests, then 100 measured:

| pair | 2.4.59 p50 / p95 | 2.4.60 p50 / p95 | Δ p50 |
|---|---|---|---|
| 1 | 23.5 / 48.2 ms | 36.1 / 70.8 ms | +12.6 ms (+54%) |
| 2 | 13.8 / 20.6 ms | 17.7 / 25.0 ms | +3.9 ms (+28%) |

Between-pair variance is large, because background load on a shared workstation shifts both arms.
The direction is consistent, and the CPU attribution is the firmer evidence. **State it as a range:
+4 to +13 ms per bundle at p50.**

**Recommended fix:** cache the heading-path → anchor map per `(slug, page version)`. The page
version is already resolved per section for the citation, so a page that is unchanged since the
last bundle costs one map lookup instead of a markdown parse. Also take the body with a split that
skips the YAML parse, since only the text after the closing `---` is needed.

## Finding 2: since 2.4.59, `shutdown.sh` leaves the Tomcat JVM running (bare metal only)

This surfaced on the first redeploy:
1. `bin/redeploy.sh` waits only for port 8080 to be released, then starts a second JVM.
2. The old JVM still holds the ontology TDB2 lock (`tdb.lock held by process …`).
3. Knowledge-graph initialization in the new JVM fails.
4. `/knowledge-mcp` comes up with **10 tools, and no bundle service** (`/api/bundle` → 503). The
   only symptoms are a WARN and a 503.

**Cause:** the old JVM's only non-daemon threads are `streamable-http-server-transport-session-sweeper-1`
and `-2`, one per MCP endpoint. MCP Java SDK 2.1.0, adopted in 2.4.59, runs its idle-session sweeper
on `Schedulers.newSingle(...)`, which creates a non-daemon thread. Its `closeGracefully()` disposes
the subscription but never the scheduler. Every fresh JVM in this run reproduced the hang: none
exited on `shutdown.sh`, and all exited on SIGTERM.

**Production (Docker) is not affected:** SIGTERM exits the JVM regardless of non-daemon threads,
and the 2.4.60 deploy started cleanly with 22 tools. Bare-metal installs that stop Tomcat with
`shutdown.sh` (`bin/redeploy.sh`, `bin/deploy-local.sh`) are affected.

**This run's workaround:** a stop helper that sends SIGTERM to any Tomcat JVM still alive 20 s after
`shutdown.sh`. **Fix to make:** on context destroy, dispose the sweeper's scheduler, or have the
SDK's single schedulers created as daemon threads. Either way, add a test that the webapp leaves no
non-daemon threads after shutdown.

## Running it on bare metal (notes for the next run)

- `loadtest/loadtest.env` points at docker2. For a local run, swap in `BASE_URL=http://localhost:8080`
  and a locally minted key (`POST /api/self/apikeys`, scope `all`), then restore the file.
- JFR writes to `wikantik.profiling.dir`, which is read only as a `-D` property. The default
  `/var/wikantik/profiling` does not exist on bare metal, so export
  `CATALINA_OPTS=-Dwikantik.profiling.dir=…/tomcat/wikantik-work/profiling` before starting Tomcat.
- `profile-iteration.sh`'s per-surface latency table comes from Prometheus, which is not available
  locally. Measure a surface directly instead, as the bundle benchmark above does.
