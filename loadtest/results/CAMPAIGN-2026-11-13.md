# Soak + profiling run 2026-11-13: the app without the Knowledge Graph (2.5.17-SNAPSHOT)

Question: with the Knowledge Graph and every chat-model path gone (2.5.13–2.5.15), where does
the CPU go now, does anything leak over an hour of mixed load, and is the production sizing
(3G container, `MaxRAMPercentage=50` ≈ 1.5G heap, chosen while KG extraction still ran) still
right?

## Environment and method

- **Target:** local bare-metal Tomcat 11, k6 co-resident (docker2 and the 18080 stack were
  unreachable, and docker1 serves real traffic). Absolute RPS is k6-confounded; A/B deltas,
  CPU composition and memory trends are the trustworthy outputs.
- **Corpus:** 1,198 repo pages, 18,627 chunks all embedded (`qwen3-embedding:0.6b`), dense
  backend `lucene-hnsw` (as docker1). Ontology rebuild: 4,176 named graphs in 0.4 s (8,733
  graphs and 6.5 min on 2026-10-22, before the KG tables were dropped).
- **JVM, mirroring prod:** `-Xmx1536m -XX:NativeMemoryTracking=summary -Xlog:gc*,safepoint`,
  continuous JFR, `wikantik.collab.enabled=true`.
- **Profiling iterations:** `bin/profile-iteration.sh` 3 min, 40 read + 10 admin VUs, after the
  documented warm-up and a check that bundles show live dense retrieval.
- **Soaks:** 60 min, 40 read + 10 admin + 2 write VUs (writes refused, see Finding 2 item 4), fresh JVM each, a sampler every 30 s
  (RSS, threads, fds, heap/old/committed/live, GC, backpressure, PG connections, on-disk sizes)
  and an NMT summary every 5 min. Raw series: `kgless-soak{1,2}-2517/samples.csv`.

The KG removal left one new hot path behind, and it was the largest CPU consumer in the app:
**−41% CPU per request, −30% mean and −38% p95 latency** after fixing it. Both soaks were flat
and leak-free; production has heap and RSS headroom to spare.

## Finding 1: "Similar pages" re-ranked the whole corpus on every call (fixed)

`PageEmbeddingSimilarity.similarTo` — the centroid-cosine replacement for KG relatedness —
scored every page centroid and sorted the full list on each call. Context retrieval calls it
once per result page on every request (`DefaultContextRetrievalService.retrieve` →
`RelatedPagesFinder.fetchRelatedPagesBatch` → `fetchRelatedPages`), so the baseline profile
spent **~44% of all CPU** there: `PageCentroidLoader.dot` 34.9% + `similarTo` 9.2% (1,319 of
1,323 samples via `RelatedPagesFinder`).

A page's ranking depends only on the page and the centroid snapshot, which is already cached
for 10 minutes. The fix memoises each page's top-200 neighbours inside that snapshot
(`computeIfAbsent`, dropped with the snapshot on refresh); the caller's `accept` filter and
`limit` stay per call, so ACL filtering is unchanged. Memory is bounded by pages × 200
entries: 40,200 `ScoredPage` objects (~1 MB) after the soak. TDD:
`rankingIsComputedOncePerPagePerSnapshotWhileTheFilterStaysPerCall` failed against the old
code (3 rankings for 3 calls) and passes after.

**Where CPU goes now** (memo build): HNSW `topKChunks` 33% (436 samples via
`HybridSearchService.rerankWithChunks`, ~87 via `ContributingChunkAssembler`'s fallback ANN, 54
via the bundle chunk source); `WikiLinkSyntax.findAll` 11.7%, almost all from the admin
full-corpus `BrokenBlockRefs` audit; audit `verifyChain` ~5.5%; YAML frontmatter parse 2.1%;
bcrypt 1.6%. Without the operator-only audits, the rate is ~153 samples / 1k requests, which
matches the 2026-10-22 campaign.

**Levers not pulled:** `hybrid.dense.chunk-top` (500) and quantization stay as they are. The
2026-09-25 campaign measured both as dead levers (iteration 4: chunk-top 500→200 gave no CPU
change and no recall change). The HNSW cost scales with graph traversal, not k.

## Finding 2: the load harness had drifted and was silently measuring less than it claimed (fixed)

1. **Wrong host.** `bin/loadtest.sh` and `bin/profile-iteration.sh` sourced
   `loadtest/loadtest.env` *after* the caller's settings, so `BASE_URL=…` and `--base-url`
   were overridden by the file's `192.168.0.5:18080`. Now the caller's exported values win,
   the file fills the gaps, and exporting a variable empty disables it
   (`K6_PROMETHEUS_RW_SERVER_URL=`). Pinned by `bin/tests/test-loadtest.sh` (7 checks; red on
   the old scripts: profile-iteration's JFR start and its k6 run went to the env-file host).
2. **Writes wrote nothing.** The admin MCP tools renamed `pageName`/`pageNames` to
   `slug`/`slugs`. `read_page`, `get_backlinks`, `write_pages` and `delete_pages` were all
   rejected by `ToolInputValidator`. The checks only asserted `status !== 0`, so they passed.
   Arguments are fixed, and checks now require a 200 with no JSON-RPC or tool error
   (`mcpToolOk`).
3. **Cache flush was malformed.** `adminCacheFlush` sent a null body with a query string. It
   now POSTs `{"cache":"wikantik.renderingCache"}`.
4. **Writes still wrote nothing after (2), found after both soaks.** The write bodies put
   display `$$` inline with prose, which the save-time math validator refuses
   (`math.display.notIsolated`). `write_pages` reports a refused page inside an `isError:false`
   result (`created:false`, `summary.failedCount:1`), and the check from (2) looked only at
   top-level errors. This is why `wikantik_page_edits_total`/`deletes_total` stayed at 0 and
   the audit log had no `page.save` rows during the soaks: **the counters were right**. The
   bodies and `mcpToolOk` moved to the k6-free `loadtest/lib/mcp-result.js`, pinned by
   `loadtest/mcp-result.test.mjs` (red on the old check and bodies). A 50 s k6 write burst
   afterwards saved and deleted 25 pages, and the counters and audit rows moved to match.

**Neither soak exercised real writes.** The writes were refused by the pre-save filters, after
the structural-spine filter but before storage, post-save listeners, reindex and embedding. The
soaks measure the read and admin load plus about one refused save per second.

## Soaks: no leak, bounded growth

| | soak 1 (MCP args broken) | soak 2 (bodies refused) |
|---|---:|---:|
| requests / failed | 205,089 / 0.32% | 205,433 / 0.33% |
| checks | 100% of 182,343 | 100% of 186,017 (the write checks passed falsely, item 4) |
| avg / p95 | 6.35 / 20.69 ms | 6.57 / 20.52 ms |
| RSS start → peak | 1,335 → 1,811 MB | 1,155 → 1,974 MB |
| heap committed | 637 → 951 MB | 579 → 1,050 MB |
| post-GC floor (10-min buckets) | 196 → 259 MB, flat last 20 min | 213 → 273 MB, decelerating |
| live set after full GC (end) | — | **239 MB** |
| GC | 0 full, 0 to-space exhausted, young max 29 ms | 0 full, 0 to-space exhausted, young p99 7.4 ms, max 16.6 ms |
| threads / fds / PG conns | 107–123 / ~220 / 7–9 | 98–131 / ~240 / 22 (pool idle) |
| backpressure / rate-limit rejections | 0 / 0 | 0 / 0 |
| app ERROR lines | 0 | 0 |

- **Native memory is flat.** Between the first and last NMT summary, committed growth is the
  Java heap (+410 MB in soak 2) plus GC structures (+10 MB). Class, thread, code, metaspace and
  symbol are unchanged. RSS growth is G1 expanding the committed heap, not a native leak.
- **What raises the heap floor is anonymous HTTP sessions.** k6 drops cookies per iteration, so
  readers mint sessions: **~52,000 live `StandardSession`/`WikiSession` pairs** at the end of
  soak 2. With `<session-timeout>60</session-timeout>` they start expiring exactly as an
  hour-long soak ends, which explains the decelerating floor. Cookieless crawlers in prod
  behave the same way, so the session table is sized by crawler rate × 60 min. This is an
  observation, not a defect: at prod's request rates it is small, but it is the first thing
  to grow under a crawler surge.
- **On-disk:** chunk and embedding counts are unchanged (18,627), as expected with no saves. The DB grew 519 → 544 MB in
  an hour, driven by `audit_log` and `retrieval_query_log` rows, both product tables by design.
  TDB2 stayed at 55 MB. No `LoadTestK6*` pages were left in `docs/wikantik-pages`.

## Sizing recommendation

The live set is ~240–300 MB against a 1.5G heap. Peak RSS was ~2.0G against the 3G container
limit, under ~50 req/s, which is far above prod's rate. **Keep the current prod settings**
(3G, `MaxRAMPercentage=50`); nothing in either soak argues for change, and the extra ~1G
outside the heap is page cache for the mmapped Lucene/HNSW indexes. If memory needs to be
reclaimed later, the data supports **2.5G with `MaxRAMPercentage=45` (~1.1G heap, ~4× the
live set)**. Do not return to 2G: at a 1.5G heap the soak's RSS would exceed it, which is the
eviction pattern seen before the KG removal. GC needs no tuning: pause time was ~0.4% of wall
clock with a single-digit-ms p99.

## Open items (not fixed here)

- **A soak with real writes is still owed.** Rerun soak 2 with the fixed harness to measure
  save, reindex and embedding growth under sustained writes.
- Admin MCP tool descriptions (`ReadPageTool`, `GetBacklinksTool`, `WritePagesTool`,
  `DeletePagesTool`) still show `pageName` in their example payloads, which probably caused the
  harness drift.
- The admin full-corpus audits (`BrokenBlockRefs`, audit `verifyChain`) dominate admin-scenario
  CPU and could be cached like `pagesWithoutFrontmatter`. Low priority because they are
  operator-only.
- The harness MCP `initialize` asks for an unsupported protocol version (98 WARNs per hour).
  It is harmless.
- Misnamed KG/LLM leftovers (rename deferred by decision): `wikantik.admin.kg.*` cache TTL,
  `wikantik.llm_activity.*` (now only embedding calls), `wikantik_hub_summary_synthesis_total`,
  and stale "batch extraction job" Javadoc in `ContentChunkRepository`.
