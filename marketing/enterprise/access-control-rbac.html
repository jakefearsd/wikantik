RBAC & access control: policy grants, ACLs, groups

Wikantik enforces access control at four layers — role-level policy grants stored in the database, page-level ACLs written inline in page content, managed groups, and private clusters that hide whole sections of the wiki — all checked consistently across the UI, REST API, search, agent endpoints, and every admin surface.

Layers of access control

Most wiki platforms have one or two access knobs: "can edit" and "can admin." Wikantik has a full permission model because the situations that enterprise teams actually face — restricting a sensitive runbook to a single team, granting an external user read-only access, letting a bot write without giving it delete rights — require genuine granularity.

The layers compose: policy grants set the baseline for each role, page ACLs narrow it for individual pages, groups make it practical to assign permissions to teams rather than individuals, and private clusters close off a whole topic area at once.

The permission model

Wikantik uses JAAS-based authorization with two sets of named permissions:

Page permissions

Each page operation requires a specific permission, checked before the operation proceeds:

  • view — read the page content
  • comment — add a comment
  • edit — modify the page body
  • modify — change page metadata
  • upload — attach files
  • rename — rename or move the page
  • delete — delete the page

Wiki permissions

Broader capability permissions govern actions that span pages:

  • createPages, createGroups, editPreferences, editProfile, login

Policy grants — database-backed, UI-managed

Default role permissions are stored in the policy_grants table in PostgreSQL. The admin UI at Admin → Security (/admin/security) exposes a grid for managing these grants: which roles get which permissions by default.

Because the grants live in the database rather than a config file, changes take effect immediately — no redeploy required. An admin can tighten or loosen role defaults at runtime, and every change is visible to any query on the policy_grants table. Database-backed grants are always active when a datasource is configured, which is the default for all production deployments.

Grants can also be scoped to one admin area. A grant of permission type admin with a target such as insights opens only /admin/insights/*; everything else under /admin keeps requiring AllPermission, so a shipper or service account does not need to be a full administrator.

Bootstrap admin override. The wikantik.admin.bootstrap property gives the named user AllPermission for a limited window after startup (wikantik.admin.bootstrap.maxAgeSeconds, default 24 hours) so a fresh or locked-out installation can be recovered. Leave it blank once a real admin account is confirmed working.

Page-level ACLs

Individual pages can restrict themselves with inline ACL directives. The syntax is embedded directly in the page body:

[{ALLOW view Admin}]
[{ALLOW edit Engineering}]

When a page carries an ACL, a user needs both the matching role or group grant and an ACL entry that names one of their principals. Name groups rather than people: a user entry in an ACL matches only the session whose login is exactly that name, and a display name or wiki name grants nobody anything.

The REST API enforces these ACLs on every request via RestServletBase.checkPagePermission(), and /wiki/{slug}?format=md|json answers a restricted page with a 404.

One reader, and an unreadable rule locks the page

A page's access rules are read from its text exactly once per version. A render never sets them, so what is enforced no longer depends on whether the page was rendered first. Plain rules are honoured as written: a one-line directive, a rule wrapped over several lines, ALLOW or the permission in any case. Directive-shaped text the reader cannot interpret with confidence (a DENY, a rule in frontmatter or in an HTML block, a wrapped rule where a line break falls inside a name) locks the page to administrators until it is fixed. Commenting a rule out with %%comment%% does not disable it.

A save cannot lock a page by accident: the save pipeline (editor, REST, MCP and the importer) refuses text that adds a rule the reader cannot read, with an ACCESS_RULE_SHAPE violation that says which line and how to write it instead. Administrators see a banner on a locked page listing each reason, and GET /admin/content/locked-pages lists every locked page.

The rules name people by login, so their text is removed from what readers without edit on the page can see: the page API, ?format= output, diffs, vault exports and /tools/get_page. Chunks, embeddings, the search index and the agent projection never contain them.

Private clusters

Set wikantik.access.privateClusters to a list of cluster paths and every page in those clusters, sub-clusters and each cluster's hub page included, becomes visible only to administrators and to the groups named in wikantik.access.privateClusters.viewers. It applies to every page action, not just viewing.

  • One gate. The rule lives in a single class, PrivateClusterGate, inside the authorization manager, so it applies on every surface: pages, ?format=, search, sitemap and feeds, /api/changes, the Page Graph, structure, ontology and SPARQL, context bundles and briefings.
  • A page ACL can only narrow further. It cannot re-open a private page.
  • New pages are private from the first save, because the cluster comes from the stored frontmatter.
  • The admin MCP bypasses page permissions by design, so administrator-equivalent tooling keeps working. Readers outside the viewer set get a 404 on a link to a private page.
  • Both lists are read at startup, so a change needs a restart followed by an ontology rebuild.

Groups

Database-backed groups (stored in groups + group_members tables) let you assign permissions to teams. You can reference a group name in a page ACL the same way you reference a role. Members are stored by login name, and the group editor rejects an entry that is not an existing login. Groups are managed through the admin UI and can be provisioned via SCIM from your IdP.

One explicit boundary: administrator access is membership of the wiki group named Admin (the default policy grants it AllPermission), and SCIM never writes that group — a SCIM create, replace, patch or delete aimed at Admin is refused with HTTP 403 and audited. All other groups, SCIM-provisioned or manual, route through GroupManager only and never modify the roles table; they carry only what policy grants and page ACLs give them. The Admin group is managed in the admin UI.

Enforced everywhere

The access control model is applied at every surface:

  • UI — the React SPA checks permissions before rendering edit controls; the server also enforces them independently.
  • REST API (/api/*) — every endpoint calls checkPagePermission() with the authenticated principal before performing any operation. The REST surface uses a session or HTTP Basic login; it does not accept API keys.
  • Admin surface (/admin/*) — protected by AdminAuthFilter, which requires AllPermission (membership of the Admin group) or a scoped admin grant for that one area.
  • Retrieval and agent surfaces — the knowledge MCP, /api/bundle, briefings and search run candidates through the same view gate, so a page a caller cannot see never reaches an agent's context.

Keys and scopes for agents

Programmatic callers use API keys, SHA-256 hashed at rest and shown once. Each key carries a scope, and the narrowest one that does the job is the right one:

  • mcp_read — /knowledge-mcp only, read-only.
  • mcp_admin — the full admin MCP at /wikantik-admin-mcp, and /knowledge-mcp too. The MCP scopes are a hierarchy: mcp_read sits inside mcp_admin, never the reverse.
  • tools — the OpenAPI /tools/* endpoints only.
  • work — work management only (/api/work/* and /work-mcp). It matches only itself and all: a work key is useless on the other endpoints, and no other scope reaches work.
  • all — every key-protected surface.

Non-administrators can mint only tools, mcp_read and work keys; mcp_admin and all are issued by an administrator. Key issuance and revocation are written to the audit log. The older mcp scope name is still accepted as an alias for mcp_admin, and every use of it is logged as a warning.

Work management roles

When the optional work module is on, projects have their own roles, separate from wiki permissions: viewer (reads), member (reads, edits, comments, moves cards), lead (also changes the project's policy and settings) and reporter (files requests and follows only what they filed). People who are not in a project get a 404, never a 403, and wiki administrators see everything.

Agents are registered identities with their own token (it starts with wka_). Whoever registers an agent is its sponsor, and the agent can never do or see more than its sponsor can. An agent holds only viewer or member in a project and can never be a reporter. See work management.

People are shown by display name

Public identity is the display name. Login names (an email address under Google sign-in) are shown only to their owner and to administrators, and authorship is stored by login but resolved to a display name on every reader surface, the public ontology included. Display names are unique and cannot impersonate a login, role or group. When an account is deleted its content shows "former member", and the login cannot be registered again.

Frequently asked questions

How are default role permissions managed?

Default role permissions are stored in the policy_grants table in PostgreSQL and managed through the admin UI at /admin/security. Changes take effect immediately without redeploying the application, and the full grant configuration is auditable.

Can I restrict a single page to a specific group?

Yes. Inline ACL syntax in the page body controls per-page access: [{ALLOW view Admin}] restricts view permission to the Admin role, and a group name works the same way. You can combine multiple ACL lines for different permissions. To restrict a whole topic area, list its cluster in wikantik.access.privateClusters instead. The REST API enforces these ACLs via RestServletBase.checkPagePermission() on every request.

How does Wikantik prevent privilege escalation through groups?

Groups (including SCIM-provisioned groups) route exclusively through GroupManager and the groups/group_members tables. The roles table is never modified by group operations. Administrator access is membership of the wiki group named Admin, and SCIM is refused (HTTP 403) any write to that group, so an IdP cannot grant or revoke it — only the admin UI can.
