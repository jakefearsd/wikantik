Security hardening: NIST passwords, CSP, safe deserialization

Security that requires constant tuning isn't really secure — it just moves the risk to whoever forgot to tune it. Wikantik ships hardened by default: password validation grounded in NIST 800-63B, HTTP security headers active on every response, and deserialization filtered at the JVM level before any object graph is inflated.

Secure by default

The wikantik-http module is a dedicated servlet filter chain that sits in front of every request. CSRF protection, CORS, Content Security Policy, and a standard set of security headers are active without any configuration. There is no "enable security mode" switch to forget to flip.

This section covers each hardening layer: what it is, how it is implemented in Wikantik, and what threat it addresses.

Passwords done right: NIST 800-63B

NIST Special Publication 800-63B is the US government's digital identity guideline. Its key insight is that the password rules that organizations traditionally enforced — mandatory rotation every 90 days, required special characters, maximum length restrictions — actually make passwords weaker, not stronger. Users respond to burdensome rules with predictable patterns: Password1!, Summer2024#.

Wikantik's password validation follows the current NIST guidance:

  • Minimum length is enforced.
  • Common-password blocklist — new passwords are checked against a list of known breached and trivially guessable passwords. password, 123456, and their obvious variants are rejected.
  • Mandatory rotation and arbitrary complexity rules are not enforced — NIST explicitly recommends against them.
  • Stored as bcrypt — passwords are hashed with bcrypt (work factor tuned to roughly a quarter-second per hash), never reversible encryption or a bare digest. Installs upgraded from older builds re-hash legacy salted SHA-256 hashes to bcrypt transparently on the owner's next login; salted SHA-1 hashes are no longer accepted.

This means your team's passwords are longer and more unique in practice, because they weren't forced into a corner by rules that reward gaming the system.

No default credential past first login

The most common way a self-hosted application gets compromised isn't an exotic exploit — it's a shipped default password that nobody changed. Wikantik closes that gap by construction. A fresh install seeds exactly one account, and that account is flagged so its first login requires choosing a new password before anything else works.

Until the password is changed, a MustChangePasswordFilter gates /api/* and /admin/* with 403 PASSWORD_CHANGE_REQUIRED, exempting only the auth surface needed to fix the situation. The replacement is validated against the same NIST 800-63B rules and blocklist as any other password, so the seeded default cannot simply be re-chosen. The net effect: no Wikantik deployment runs with a known default credential past initial setup.

Deserialization filtering

Java deserialization vulnerabilities have enabled remote code execution in countless Java applications over the past decade — not because the applications were poorly written, but because Java's ObjectInputStream will inflate any class on the classpath if you ask it to, and a sufficiently clever chain of objects can trigger arbitrary code execution.

Wikantik applies ObjectInputFilter whitelists to every ObjectInputStream usage. Only an explicit allowlist of classes can be deserialized. Any attempt to deserialize a class outside the allowlist is rejected before the object is constructed. This closes the gadget-chain attack surface at the JVM level, independent of what's on the classpath.

CSRF, CORS, CSP, and security headers

The wikantik-http servlet filter chain applies the following on every response:

CSRF — synchronizer token pattern

State-changing requests (POST, PUT, PATCH, DELETE) must carry a valid session-bound CSRF token. The token is generated per session and checked before any mutation proceeds. The one explicit exception is the SAML /sso/callback endpoint: the IdP-signed SAML assertion is its own CSRF defense (an attacker cannot forge a valid IdP signature), so a synchronizer token would add friction without adding security.

CORS

Cross-origin access to the REST API is allowlist-only: with wikantik.cors.allowedOrigins blank (the default) no cross-origin requests are allowed, and Access-Control-Allow-Credentials is never set, so the session cookie is never exposed to cross-origin scripts.

Content Security Policy

A Content Security Policy header is sent with every HTML response, restricting which origins scripts, styles, and other resources can be loaded from. CSP is the primary defense against XSS attacks that manage to inject content — even if an attacker injects a <script> tag, the browser refuses to execute it if the source doesn't match the policy.

Standard security headers

Additional headers applied on every response include:

  • X-Content-Type-Options: nosniff — prevents MIME-type sniffing
  • X-Frame-Options: DENY — blocks clickjacking
  • Referrer-Policy — controls referrer leakage
  • Strict-Transport-Security — enforces HTTPS on compliant browsers
  • Cross-Origin-Embedder-Policy and Cross-Origin-Resource-Policy: same-origin — keep other origins from embedding your resources

Session management

Wikantik rotates the HTTP session on every authentication event — both local password login and SSO callback. The old session ID is invalidated and a fresh one is issued before any privileged state is written. This closes the session fixation attack, where an attacker tricks a user into using a pre-seeded session token.

The session cookie is HttpOnly, cookie-only (no URL rewriting) and issued SameSite=Lax; the optional remember-me cookie is HttpOnly, SameSite=Lax and holds an opaque, server-validated token. Requests that authenticate with an API key or a work agent's token carry no principal and never become a session, so a credential cannot be turned into a browser login.

Authentication is JAAS-based. Pluggable login modules support local database, SSO (pac4j), and container-managed authentication. All modules coexist and can be active simultaneously.

Access control enforced on the read path — including the agent surface

View ACLs are not just a UI concern. Wikantik enforces page view permissions on every read surface: the REST read endpoints (page fetch, diff, history, backlinks, recent-changes, search, and the agent projection) and — critically — the machine surfaces an AI agent uses. The /knowledge-mcp retrieval and navigation tools and the /api/bundle context bundle all run candidate results through the same session view gate.

The practical guarantee: a page a caller is not permitted to see never appears in their search results, their retrieval, or an agent's assembled context bundle — restricted content cannot leak into a RAG pipeline through a side door. Restricted hub descriptors are likewise redacted from cluster listings.

Access rules you can trust

Page access rules ([{ALLOW view Admin}]) have exactly one reader. The rules come only from the page text, read once per version, and a render never sets them, so what is enforced no longer depends on whether a page was rendered first. If the text contains directive-shaped content the reader cannot interpret with confidence (a DENY, a rule in frontmatter, math or an HTML block, a wrapped rule with an ambiguous name), the page locks to administrators until it is fixed. Commenting a rule out does not disable it. A save that would add such a rule is refused with a message saying how to write it, so an editor cannot lock a page by accident, and administrators see why any locked page is locked. Details are on the access control page.

Whole clusters can be closed off with wikantik.access.privateClusters: one gate, inside the authorization manager, applied to every surface from pages and search to feeds, the Page Graph, SPARQL and context bundles. A page ACL can only narrow it further.

Identity: display names and former members

People are shown to each other by display name. Login names (an email address under Google sign-in) are visible only to their owner and to administrators, across the page, history, search, comment, feed, MCP, /tools/* and ontology surfaces. Access-rule text, which names people by login, is stripped from anything returned to a caller who cannot edit the page, and never reaches the search index, chunks, embeddings or agent projections. When an account is deleted, the login is recorded so old content shows "former member" and nobody can register that login again, whether by self-registration, an admin, SCIM, a rename or SSO.

Bounded work on untrusted content

  • Markdown render cost is bounded. A crafted run of braces could once make parsing quadratic or overflow the stack, and a very long paragraph could take minutes to parse. Parses now run under a budget; over budget, a page is re-parsed without attributes or shown as escaped text, and every parser is built through one class that an architecture test enforces.
  • Diagrams are sandboxed. ```mermaid fences are validated fail-closed on the server and in the browser and run at Mermaid's antiscript level. ```plantuml fences are drawn server-side in PlantUML's SANDBOX profile with Graphviz unreachable: no file, URL or environment access, output SVG scrubbed to an allow-list and added after the HTML sanitizer, with a per-diagram timeout and per-page limits. A source that fails validation is shown as source, with the reason.
  • Render caches skip viewer-dependent output. A render that consults the caller's session or permissions is flagged and excluded from the shared caches, so an ACL-gated render for one user is never served from cache to another.
  • Rate limiting. Per-client sliding-window limits cover /api/*, /export/* and /sparql, with a tighter tier for the expensive search, bundle and SPARQL paths. /metrics and /api/health answer only on loopback and private networks.

Risky features ship off or fenced in

  • JDBC plugin disabled by default. The [{JDBCPlugin}] plugin, which runs page-authored SQL against the wiki's datasource, is off (wikantik.plugin.jdbc.enabled) and is checked before anything else. Enable it only if you accept that a high-privilege database role will run editor-supplied SQL.
  • SSRF protection on connector fetches. An EgressGuard validates every outbound HTTP(S) request a connector makes: non-http(s) schemes are rejected, and any host resolving to loopback, private, link-local (including the 169.254.169.254 cloud metadata address), multicast, or IPv6 unique-local addresses is blocked by default. Every redirect hop is re-validated. An operator can allow an internal crawl deliberately with a JVM system property.
  • Scoped API keys. mcp_read reaches the knowledge MCP read-only, mcp_admin the full admin MCP, tools the OpenAPI endpoints, and work only work management. Self-service users can mint only the narrow ones, and every use of the legacy mcp alias is logged.
  • Outbound and inbound work-management paths. Webhooks are off by default, https only, pass the same egress guard and are signed with HMAC-SHA256. The code-host hook accepts only a body signed with the product's secret, and every refusal is one identical 404, so it does not reveal which products exist.
  • Admin areas can be granted one at a time. A scoped admin policy grant opens a single /admin/* area without making the holder a full administrator.

Defense in depth

The hardening described here is one layer of a broader stack. For a complete picture, see:

  • SSO (SAML / OIDC) — session rotation, fail-closed account binding, CSRF handling for SAML
  • RBAC & access control — JAAS permissions, policy grants, page ACLs
  • Tamper-evident audit log — authentication events, access denials, and admin actions recorded in a hash chain you can verify
  • SCIM provisioning — deactivation enforced at every login path; SCIM can never write the Admin group

Frequently asked questions

What is NIST 800-63B password validation?

NIST SP 800-63B is the US government's digital identity guideline. Its password rules focus on real-world security: minimum length matters, complexity rules don't. Wikantik enforces a minimum length requirement and checks new passwords against a common-password blocklist. Mandatory rotation and special-character rules are not enforced, as NIST 800-63B explicitly recommends against them.

How does Wikantik protect against CSRF attacks?

The wikantik-http module includes a CSRF servlet filter that implements the synchronizer-token pattern: every state-changing request must carry a valid session-bound token. The one exception is the SAML /sso/callback endpoint, which is exempt because the IdP-signed SAML assertion is its own CSRF defense.

What is deserialization filtering and why does it matter?

Java deserialization vulnerabilities have been the source of critical remote code execution exploits in many Java applications. Wikantik applies ObjectInputFilter whitelists on all ObjectInputStream usage, restricting which classes can be deserialized to an explicit allowlist. This closes the attack surface for gadget-chain exploits against any serialized data Wikantik processes.
