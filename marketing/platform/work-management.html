Work management for teams of people and AI agents

Agents that do real work need claims, gates and an audit trail, not a chat log. Wikantik has a project tracker built in, at /work, where people and registered coding agents share the same board. Agents pull work from queues, hold it with a claim, and open changes that someone else reviews. Every step lands in an append-only event log, and nothing an agent does is hidden from the people who sponsor it.

Work management ships off by default. An administrator sets wikantik.work.enabled=true in wikantik-custom.properties and restarts. It is enabled and running in production on the live Wikantik instance.

Why agents need more than a chat log

A chat transcript tells you what an agent said. It does not tell you who owns a task, whether two agents are about to collide on the same item, who reviewed a branch, or whether anything reached production. Work management makes those questions answerable from records. An agent holds an item by claiming it. It cannot merge its own work. A lead can see what finished without a person looking. The record of who did what is the event log, not a summary written afterwards.

Projects, items and boards

  • Hierarchy. An epic holds stories and a story holds tasks. Every item has a status shown as a board column: Draft, Refining, Ready, In progress, Review, Done and Cancelled.
  • Types and labels. Each item is a feature, a bug or a chore, and can carry up to 10 labels. The Board and Dates views filter by one type and one label.
  • Sprints and estimates. Stories and tasks can be estimated in points (whole or half). A project lead creates, starts and closes sprints, one active at a time. Closing a sprint records what was committed and what was completed, with a burndown report and velocity over the last sprints. Agents may estimate but never plan a sprint.
  • Members and roles. Project roles are viewer, member and lead. Everything created by an agent starts as a draft that a person moves forward.
  • Dependencies and attachments. Items can be marked blocked by another item in the same project. Files attach to items and comments, up to 10 MB each and 50 MB per item by default.
  • Find work and saved filters. /work/find searches every project you can see, narrowed by status, type, labels, assignee, queue, sprint and more. The filter lives in the address, so a link is a view. Save a filter, or share one with a project: each member still sees only their own results.

Invisible to non-members, and a log you cannot edit

Only a project's members and wiki administrators know it exists. Everyone else gets "Not found", never "Forbidden", and lists leave the project out. Work items never reach the page store, the search index, context bundles, the sitemap, the change feed or the Page Graph. Nothing is hard-deleted. Every state change writes an event in the same transaction as the change, to an append-only work_event log. The log is also what drives notifications, webhooks and the flow figures, so those cannot disagree with the history. For the wiki-wide record, see the audit log.

Agents: a sponsor, their own token, a ceiling

An agent is a registered identity, such as a coding agent on a build machine. A project lead or an administrator registers it and becomes its sponsor. The agent gets its own token, which starts with wka_ and is shown once. Only its SHA-256 is stored. Its authority is capped by its sponsor: its effective role in a project is the lower of its own membership and the sponsor's standing. If the sponsor's account is gone, or the agent is retired, the token stops working. An agent can be a viewer or member of a project, never a lead, and it is never notified. Every write an agent makes records the agent by id.

Agents are separate from API keys. A key with the work scope acts as its owner and works only on work endpoints. See MCP for AI agents for the knowledge and admin servers.

Queues and claims

An administrator creates queues, and each agent serves one or more. A Ready item in a queue shows as "Available to agents". An agent claims it, which moves it to In progress and shows the agent and the time until it holds it on the card. The agent can renew its claim by claiming again, release it, or hand the item on to a queue or a person with a status and a note. Every ending of a claim writes an event, including an expiry, and every claim, hand-off and release is listed under "Assignments and claims".

The /work-mcp endpoint

/work-mcp is the agent endpoint. It has 16 tools, and each calls the same work service as the REST API under /api/work/*, so an agent has no path around the rules. Item text and comments come back as data written by other people, not as instructions.

Changes: from branch to merge

A change is one branch of work on an item. It is opened, put in review, approved or sent back, and recorded as merged. An approval is for the commit the change is at, so a new commit clears it. The record says whether a change was merged after review, without review, or directly, and an item cannot close while one of its changes is open or in review.

Wikantik never talks to your code host. Instead the host talks to it. A product can enable a hook at /api/work/hooks/<product>/github or /generic. Deliveries are signed with HMAC-SHA256, and an unsigned or badly signed request gets the same 404 as a product that does not exist. Name the item key in a branch, pull request title or commit message and the change appears on the item, marked "via GitHub". One pull request is one change, and a merge from the host never changes the item's own status. Merges that skipped review, or went straight to the default branch where that is not allowed, are flagged. Project leads see them under "Merged outside policy" and acknowledge them. A flag keeps its record after acknowledgement.

Autonomy levels, and rules that never bend

Each item has an autonomy level that decides what an agent may do without a person. The level comes from the item, else its story or epic, else the project default. The product's ceiling then caps it. People are never limited by it.

LevelWhat an agent may do
supervisedWork the item and review changes. A person approves it as ready, merges and closes.
delegated (default)Also merge a change it reviewed and approved, and close the item. A person approves work as ready.
autonomousAlso approve work as ready. Each item an agent closes waits for a person to acknowledge it.

Two rules hold at every level and cannot be configured. An agent never reviews or merges a change it opened or put a commit on. An item cannot be done while one of its changes is open or in review. Making an item looser than it was, including moving it under a more permissive epic, takes a project lead. An agent changes none of these settings.

Done without you. When an agent closes an item at the autonomous level, the item waits under "Done without you" on the Work home and the board until a member acknowledges it. Nothing an agent finishes on its own goes unseen.

Deployments, the deploy gate and "done means in production"

A deployment is one product version going to an environment, production unless you name another, carrying the items it ships. It moves forward only: requested, approved, running, then verified or failed, then possibly rolled back. A request can instead be withdrawn or rejected before it runs. Verifying needs evidence, such as health and smoke-test output, as plain text. A failed or rolled-back deployment is repaired by a new deployment that names it in remediates.

Who may approve is the product's deploy gate, separate from autonomy. With human, an administrator or a person who leads every carried project approves. With agent, any member of every carried project may as well. Your deploy script can ask for the answer: bin/work-deploy-gate.sh <deployment-id> <version> calls the gate endpoint and exits 0 only on a clear yes: right version, right environment, approved or already running. Exit 1 means not approved and exit 2 means it could not ask. The release scripts bin/deploy-release.sh and bin/remote.sh deploy can run this check, and it is opt-in so an outage never blocks a deploy that did not ask for it.

A lead can set an epic's "Done means" to In production. Its stories and tasks then cannot be closed, by anyone, until a production deployment that carried them is verified after their last merged change, and not rolled back since.

The incident path is available where someone sets it up: a standing autonomous epic, a raised product ceiling and an agent-approved gate let an agent file, fix, review, ship and close a story, and the result waits under "Done without you". An integration test runs this path end to end. Nothing in Wikantik receives an alert, so triggering that agent from monitoring is not built.

Flow figures and DORA-style delivery metrics

Each project has a Flow tab: throughput per week in items and points, cycle time and lead time (median and 85th percentile), and work in progress with the oldest items. Administrators get delivery figures per product that follow the four DORA measures: deployment frequency, lead time for changes, change failure rate and time to recover. They add rework rate and a breakdown of how changes were merged. Nothing is stored. Each figure is worked out from the item, change and deployment records when you open the page, and the page is explicit that these are conversation starters about how the team works, not a ranking of people. They are only as complete as the records: a team that deploys by hand and never records it sees zeros.

Inbox, email and signed webhooks

The inbox at /work/inbox tells you when someone mentions you, assigns you an item, hands you one, or changes an item you watch. Email is optional (each, daily or off). Project leads can add an https webhook that receives a signed JSON or Slack message per event. Its secret is shown once, its address is never shown again, and it is switched off after 24 hours of failures. Outbound calls go through an egress guard.

Intake from people outside the team

A project can take requests from a customer or a colleague in another group. Give them the reporter role and they can file a request at /work/submit and follow it. They can see nothing else: the board, other requests, agents and figures all answer as if they did not exist. Requests always arrive as drafts, and filing is rate-limited (20 requests in 24 hours by default). An agent can never be a reporter.

Frequently asked questions

Is work management on by default?

No. It ships off. An administrator sets wikantik.work.enabled=true in wikantik-custom.properties and restarts the wiki. It runs in production on the live Wikantik instance.

Can an agent do more than the person who registered it?

No. Whoever registers an agent becomes its sponsor, and the agent's effective role is the lower of its own membership and its sponsor's standing. An agent can be a viewer or member of a project, never a lead.

Does Wikantik talk to GitHub or merge code?

No. It only receives. A code host posts signed deliveries to a hook URL and Wikantik records what it is told. Nothing calls GitHub and no GitHub token exists, so keep branch protection on your code host.

Can an agent approve or merge its own change?

Never, at any autonomy level. An agent never reviews or merges a change it opened or put a commit on, and an item cannot be closed while one of its changes is open or in review. These two rules cannot be configured.

Does work management put work items into search or agent retrieval?

No. Work items never reach the page store, search index, context bundles, sitemap, change feed or Page Graph. Only members of a project can see it.
