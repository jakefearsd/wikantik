# wikantik-work-mcp

Module notes, loaded when working under this directory.

- **What it is.** The MCP endpoint `/work-mcp` (`com.wikantik.work.mcp`) through which agents (with their own `wka_` tokens) and people's work-scoped API keys read and change work items. Tools call `WorkService` and nothing else; design: `docs/superpowers/specs/2026-11-15-work-management-design.md`.
- **Key-only.** `WorkMcpInitializer` builds the endpoint with `McpEndpointBootstrapper.Builder.keyOnly(true)` and scope `WORK`, which registers `KeyOnlyMcpAccessFilter` (`wikantik-mcp-core`): `mcp.access.allowUnrestricted` and `mcp.access.allowedCidrs` are ignored, so a request without a valid work key gets 403 even where those properties open the other MCP endpoints. The per-key rate limiter still applies. Never route `/work-mcp` through the config-driven `McpAccessFilter` constructors.
- **No user principal.** The request the transport sees carries the verified credential as a request attribute and has no user principal and no remote user (auth type `API_KEY`): an agent's own token arrives as `AgentTokenAuth.ATTR_AGENT_REF` (an `AgentTokenAuth.Request`), a personal `work` API key as `ApiKeyPrincipalRequest.ATTR_API_KEY_RECORD` (a `KeyRequest`). Nobody's identity is visible downstream (the twin of `WorkKeyRequest` on REST). An agent token is verified by the work module (`WikiWorkActors.agentVerifier`, handed to the filter by `McpEndpointBootstrapper.Builder.agentTokens`) and never sent to `ApiKeyService`. `KeyOnlyMcpAccessFilterTest`.
- **One session, one credential.** The filter remembers which client opened each MCP session (`key:<id>` or `agent:<id>`, so the two never collide; it reads the `Mcp-Session-Id` header as the transport writes it) and refuses any other on that session id with 403 `{"error":"This MCP session belongs to another API key"}`; the first goes on acting as itself. An unbound session id (binding expired after 2 h idle, evicted past 10,000, or dropped on `DELETE`) is bound to the first credential that uses it. The instructions file says so. `KeyOnlyMcpAccessFilterTest`, `WorkMcpSessionActorTest`, `WorkMcpIT.oneSessionServesOneKey`.
- **Off means 404.** With `wikantik.work.enabled=false` (or work failed to wire) `WikiEngine.workService()` is null, the initializer registers nothing, and `/work-mcp` is a container 404. The listener in `web.xml` must stay after `WikiBootstrapServletContextListener`.
- **The actor is resolved per tool call**, from that call's own HTTP request, never from the session: `WorkMcpActors.extract` (the transport's context extractor, run by the SDK once per request) carries the verified agent ref or key record; `WorkMcpActors.actorFor` turns it into an actor on every call (`WikiWorkActors.actorForAgent` / `actorForKey`). An agent is resolved with its sponsor as they are now, so an agent that was retired, released by its sponsor, or whose sponsor's account is gone is no actor on its next call and the tool answers `This endpoint needs a work API key.`; a sponsor lookup that did not answer is `Work is unavailable right now.` and changes nothing. There is no fallback to a person, a session, a guest or a default actor. `WorkMcpSessionActorTest` drives the real filter and transport to pin this.
- **No store access.** No class here depends on `WorkStore`, any sub-store, any `Jdbc*` class, `com.wikantik.jdbc` or `javax.sql`, and none calls `WorkClaimsService.sweepExpiredClaims()` or `sweepStanding()` (internal scheduler only). `WorkMcpAccessArchTest` enforces it.
- **Names, never logins.** `WorkMcpJson` renders people by display name, agents and queues by name; never a login, an API key id or a token. Item text (titles, bodies, comments) is returned as Markdown source and is untrusted data: the instructions file says so.
- **Allow-listed arguments.** Each tool reads only the arguments it declares (`WorkMcpArgs`: a value of the wrong type is a validation error). The twelve write tools (`claim_item`, `release_item`, `handoff_item`, `update_item`, `create_item`, `comment_on_item`, `open_change`, `update_change`, `review_change`, `merge_change`, `request_deployment`, `update_deployment`) call `WorkMcpArgs.rejectOthers` first and **refuse an undeclared argument by name** (`<field>: Unknown argument.`, or a specific reason such as "New items always start as drafts." for `status` on create or the hand-off pointer for `assignee`/`queue` on update), so an agent never believes it changed something it did not; the four read tools (`list_claimable`, `get_item`, `get_work_context`, `get_deployment`) ignore extra arguments. Identity, `actor_kind`, agent ids, versions the tool does not take, and review/autonomy fields are never arguments; the actor comes from the key (see above). Write tools take only what a person's own request takes.
- **Errors are text with a stable prefix**, mapped once in `WorkMcpTool.call`: `denied: <reason>` (policy: another agent holds the claim, "A person moves a draft forward.", a viewer writing), `<reason>: <message>` for conflicts (`stale:`, `not_claimable:`, `not_claimed:`, `archived:`, `open_changes:`, `not_approved:`, `not_in_review:`, `change_closed:`, `awaiting_deployment:`, `bad_transition:`), `<field>: <message>` for validation, `Not found.`, `This endpoint needs a work API key.`, and `Work is unavailable right now.` for anything unexpected (logged at WARN, never shown). The instructions file and each tool's description name the prefixes an agent can see; keep them in step.
- **Two log lines, both on `SecurityLog`.** A successful write tool logs `MCP_WRITE tool= action= target= author=` (through `McpAudit.logWrite`, author = the actor's name); a refused write tool logs `MCP_WORK_REFUSED tool= item= agent= kind=` (`WorkMcpLog.refused`, from `WorkMcpTool.call`; `kind` is `needs_key`, `not_found`, `denied`, `validation` or the conflict reason, never the message; every field is stripped of control characters and capped at 64, and the caller's `item` also loses whitespace and `=` so it cannot forge a field). The author is the actor's name: an agent's name, or for a work key bound to no agent its owner's login. Reads are logged at DEBUG only (`dispatch` logs a write call at INFO and a read call at DEBUG), and the security log gets `MCP_WRITE` and `MCP_WORK_REFUSED` only: a refused read writes no `MCP_WORK_REFUSED` line. A database error is logged by class and SQLState, never by its message (constraint messages carry row values). `WriteToolsAuditTest`, `WorkMcpLoggingTest`.
- **Change tools.** An item is named by `key`, a change by `change` (its number, shown by `open_change`, `get_item` and `claim_item`). `WorkMcpChanges` renders a change (people by display name, agents by name) and reads those arguments. The four tools are fenced by another agent's claim, so a reviewing agent holds the item first; the instructions file describes the hand-off. Audit actions are single tokens (`change-opened`, `change-merged-directly`, `change-updated`, `review-requested`, `change-abandoned`, `change-approved`, `changes-requested`, `change-merged`); the target is the item key for `open_change` and `change:<id>` for the rest. `ChangeToolsPostgresTest` drives the real dispatch, service and store.
- **Deployment tools.** A deployment is named by `deployment` (its number); `request_deployment` takes `items`, a list of item keys. `WorkMcpDeployments` renders one for the caller: only the carried items it can see. Evidence is returned as the text it was given, and the instructions file calls it data. `update_deployment` refuses `evidence` with any state but `verified` and `note` with `running` or `verified` (those moves record none), by name. Audit actions are `deployment-requested` and `deployment-<state>`, target `deployment:<id>`. `DeploymentToolsPostgresTest.theIncidentPathEndToEnd` runs the whole autonomous path through the real dispatch.
- **Hidden and unknown are one answer**, `Not found.`, for every tool (`WorkMcpTool` maps `WorkNotFoundException` to it).

## Adding a tool

1. Subclass `WorkMcpTool` (`name()`, `definition()`, `run(actor, args)`); put the logic in `WorkService`, not here. Use `READ_ONLY` annotations only for tools that read.
2. Add it to `WorkMcpInitializer.assembleTools(...)`.
3. Describe it in `src/main/resources/wikantik-work-mcp-instructions.txt`.

Tests that then fail until you do: `WorkMcpInstructionsDriftTest` (instructions name every tool and no unregistered one), `WorkMcpInitializerTest.assembledToolNames` (the expected set), and, in the IT module, `WorkMcpIT.EXPECTED_TOOLS` (the full list: derive the current count from `assembleTools`, do not copy it). A write tool also needs the audit call (`WorkMcpLog.written` on success; refusals are logged by the base class for any tool that reports `writes()`) and a case in `WriteToolsAuditTest`; `McpAgents.md` lists the tools. The admin MCP's `EXPECTED_TOOLS` / `InstructionsRegistryDriftTest` are about `/wikantik-admin-mcp` and are unaffected by this module.
