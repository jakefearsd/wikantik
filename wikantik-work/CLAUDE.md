# wikantik-work

Module notes, loaded when working under this directory.

- **wikantik-work** (work management): projects, epics/stories/tasks, comments, queues, agents, claims and an append-only event log in `work_*` tables (`com.wikantik.work.*`). Depends on neither `wikantik-api` nor `wikantik-main`; all database access goes through `com.wikantik.jdbc.Jdbc`. Design: `docs/superpowers/specs/2026-11-15-work-management-design.md`.
- Feature flag `wikantik.work.enabled` (default `false`); `/api/capabilities` reports it as `work`.
- Work items never reach the page store, search index, bundles, sitemap, change feed or Page Graph. Nothing is hard-deleted; `work_event` is append-only.

Rules a future change must not break:

- No dependency on `wikantik-api` or `wikantik-main`. The runtime wiring and text rendering live in `wikantik-main` (`com.wikantik.work.runtime`).
- Every caller goes through `WorkService`; `WorkStore` has no visibility check (`WorkAccessArchTest` enforces it). `WorkServiceVisibilityPostgresTest` classifies every public `WorkService` method as a read or a write and drives each read as a non-member: a new public method must be classified there.
- Non-members get **404, never 403**, and lists omit the project. Wiki Admins see everything.
- Nothing is hard-deleted; `work_event` is append-only.
- `blocked_by` links are same-project only.
- Item text renders in the "links as typed" mode (`Context.VAR_LINKS_AS_TYPED`) with page filters off, and must never do a page, title, alias, heading or attachment lookup.
- No project, product or item labels on metrics (`WorkMetrics`): cardinality and leakage.
- The activity cursor is the pair `(at, id)`, never `at` alone.
- The policy columns `default_autonomy`, `autonomy_ceiling`, `autonomy` and `allow_direct` are live (see "Changes and autonomy" below); `done_means` and `deploy_gate` are live too (see "Deployments" below).
- Every state change leaves a `work_event` in the same transaction: item changes per field; membership (`member`, values `kind:principal:role`), project settings and archive (`settings`, field in the note) as project-level events with no item. Product changes (a product has no project, and `work_event.project_id` is `NOT NULL`) are recorded in `work_product_event` (V083), one row per changed field, in the same transaction; `WorkService.productHistory` reads them (wiki admins only).
- People are named by display name in both directions (`WorkPeople`): a request's assignee, member principal (kind `user`), board filter and bare `@name` mention resolve a display name; only a wiki admin's request may also use a login. Responses (`WorkJson`) show a non-admin display names only (`mine`/`self` mark the caller). Comment mentions use the wiki's token `@[Display Name](user:<id>)`; a resolved bare mention is stored as that token, so stored text never gains a login. At most 50 distinct mentions per comment resolve.
- Comments render through `WorkRenderer` like item text (`CommentView.bodyHtml`). Parent/product `field` events store ids; `EventKeys` shows keys at read time.
- **One definition of a status move: `StatusMoves`.** "This event moved the item from status A to status B" is decided in one class, in Java (`StatusMoves.of`) and SQL (`movedSql`, `toSql`, `intoSql`): a plain `status` event, the status part of a `handoff`, a `claimed` take (ready to in progress), a `claim_expired` lapse and a `released` back to ready (not the `moved`/`reassigned` releases, whose update records the move). The flow figures (`JdbcWorkFlow`: first start, last close), the sprint burndown (`JdbcSprintHistory`) and the reporter rule (`ReporterEvents`) all read moves through it; `StatusMovesPostgresTest` compares the SQL and Java forms, the burndown read and the reporter rule over every event type. A new way to move a status must be added there, never read ad hoc.
- An archived project is read-only: refusals are `WorkConflictException` with reason `archived` (REST: 409 `reason: archived`, no `current`); a stale version is reason `stale`.

## Agents, queues and claims

Agents are registered by a project lead or an Admin (who becomes the agent's **sponsor**), serve queues, are admitted to projects as `viewer` or `member` (never `lead`, refused by the service and by the store's `putMember`) and take items from a queue by claiming them. Design of identity and authority: `docs/superpowers/specs/2026-11-16-work-agent-identity-design.md`. The agent endpoint is `/work-mcp` (`wikantik-work-mcp`); the same actions exist on `/api/work/*`.

- **An agent's identity is its own credential, and its authority is capped by its sponsor.** An agent authenticates with its own token (`AgentTokens`: prefix `wka_`, only the SHA-256 is stored, `work_agent_credential`, one live per agent, `WorkCredentialStore`). `registry().agentForToken` then `actorForAgent` are the only way a request becomes an agent actor: null (no actor at all) when the agent is retired, has no sponsor, or its sponsor's account is gone; the actor carries the sponsor resolved for this request (`Actor.sponsor()`, through `WorkDirectory.person`: groups and admin flag as they are now). No API key is, was or can become an agent: `actorForApiKey` is always the key's owner as a person, `admin` forced false. A caller never supplies `actor_kind`. A directory or store failure is `WorkUnavailableException` (REST 503, MCP "Work is unavailable right now."), never "no actor" and never cached. `ActorTest`, `WorkAgentIdentityPostgresTest`, `WorkAgentTokenIdentityPostgresTest`, `JdbcWorkCredentialsPostgresTest`.
- **The sponsor is a ceiling, never a source, and it is always looked up, never stored.** `WorkStanding` is the one resolver of an actor's role in a project and of the projects it can see: an agent's effective role is the lower of its own member row and its sponsor's standing (a wiki-admin sponsor limits nothing; an agent with no member row has nothing whoever sponsors it), and the same applies to reading. No other class of the module asks a store for a role or the visible projects (`WorkStandingSourceRuleTest`). An agent whose sponsor lacks standing gets exactly what a stranger gets (404). Who may register, edit, rotate, retire, take over and release an agent is `AgentSponsorship` (sponsor or admin; a lead takes over only an agent nobody stands behind; an agent never manages agents; an agent the caller cannot see is not found, not denied). `WorkStandingPostgresTest`, `WorkAgentRegistryPostgresTest`, `WorkServiceVisibilityPostgresTest` (its strangers include a member agent under a non-member sponsor and with none).
- **Only a human can be an admin**, structurally: `Actor`'s constructor drops `admin` unless the kind is `HUMAN`. An agent sees only projects with an `agent` member row naming it that its sponsor can also see; it gains nothing from its sponsor or from any group. `WorkServiceVisibilityPostgresTest` drives an admin-flagged agent as a stranger.
- **Attribution is by id columns, never names.** Every store write by an agent records its id (`work_event.agent_id`, `work_comment.author_agent_id`, `work_item.reporter_agent_id`, `work_item_revision.edited_by_agent_id`), and the store refuses an agent actor without one, and a person actor carrying one. Compare agents by id. `JdbcWorkStoreAttributionPostgresTest`.
- **Claimable** means: the agent is a member of the project and serves the item's queue, the item is `ready` or `review`, unclaimed and not blocked. These conditions gate a fresh take only: the holder can always renew its own claim (removing a queue from an agent does not release claims it holds). `JdbcWorkClaimsPostgresTest`, `WorkClaimsServiceTest`.
- **A claim locks, `FOR SHARE` and in this order, the agent row (`retired_at IS NULL` and still naming the sponsor the actor was resolved with), the agent's member row (role `member`), the sponsor's member rows that give them at least `member` (their own or a group's; skipped for a wiki-admin sponsor), and the project row (`archived_at IS NULL`); then the item.** An agent retired, removed or demoted, a sponsor removed, demoted or replaced, or a project archived while the claim runs therefore cannot leave the agent holding an item: the claim either lands first and the other transaction releases it, or waits and finds nothing to stand on. The store, not only the service, enforces "no claim beyond the sponsor's standing". Archiving locks the project row then the items; member writes lock their row; a sponsor change updates the agent row: there is no cycle. Keep the lock order. `JdbcWorkClaimsConcurrencyPostgresTest`, `JdbcWorkClaimsAccessPostgresTest`, `JdbcWorkClaimsSponsorPostgresTest`.
- **Every ending of a claim writes an event in the same transaction as the change**, and the claim listener and `wikantik_work_claims_total` count every ending, so the metric agrees with the log. Releases write `released`: `from_value` is `agent:<holder id>`, `to_value` the resulting status, `note` the reason: `moved` (an item update), `reassigned` (a hand-off), `access removed` (member removed or demoted), `agent retired`, `project archived` (archiving releases every claim in the project in the archive transaction, actor = the archiver), `sponsor access removed` (the sponsor's standing went: in the member transaction via `putMember`/`removeMember(…, sponsorsToRecheck)`, in the sponsor change via `WorkClaimStore.setSponsorAndRelease`, or by `sweepStanding`, where the actor recorded is the agent, as for an expiry), or a person's release note (`released` when none). A lapse writes `claim_expired`. A deliberate-release note equal to one of the six reserved words is refused (400), so a note can never pass for a consequence. Releasing or expiring touches only the claim columns, `status` and `version`. `WorkClaimListenerPostgresTest`, `JdbcWorkStoreHandoffRollbackTest`, `JdbcWorkClaimsRollbackTest`.
- **The store reports what happened; the service never infers it from its own earlier read.** `WorkClaimStore.claimWithOutcome` says whether the statement took or renewed (a renewal that lost to the sweep is a fresh take: `renewed:false`, counted CLAIMED); `WorkStore.writeItem` returns `ItemWrite` with the agent whose claim the write ended, from the row read under lock, and `WorkClaimsService.write` fires RELEASED from that. **An agent's write is fenced under the same lock**: if the locked row is claimed by a different agent the store throws `ClaimFenceException` and writes nothing; the service answers `WorkDeniedException` "This item is claimed by another agent." (a claim on a review item does not move the version, so the version check alone cannot catch it). People are never fenced. `WorkClaimRacePostgresTest`.
- **One assignment target per item**: a person (`assignee`, logins only) or a queue (`assignee_queue`). Setting one clears the other; create with both is refused. An item created with a person or queue writes `assigned`. `WorkServiceAssignmentPostgresTest`.
- **No `in_progress` in a queue without a claim.** A change of status, person or queue that would leave the item in a queue as `in_progress` (and so unclaimed: any such change ends a claim) is refused for everyone on update and hand-off: 400 `status` "Work in a queue is ready or in review until an agent claims it." Claiming is what moves queued work to `in_progress`; a holder handing its claimed item to another queue chooses `ready` or `review`. A change that moves nothing (a text edit) is not refused. `ItemTargets.requireClaimForQueuedWork`, `WorkHandoffDirectionsPostgresTest`.
- **A new item's status** is `WorkPolicy.startStatus`: a person's task or story starts `ready` (the owner's call, 2026-11-20: creating it is the person's say-so, so a queued one is claimable at once); an epic (it has no `ready`) and every agent's item start `draft`. `WorkDraftRulePostgresTest`.
- **An agent may not move an item out of `draft`** (update or hand-off, every surface): "A person moves a draft forward." ("A person cancels or moves a draft." when the move is to `cancelled`; `WorkPolicy.mayChangeStatus`). Moving an item into `draft` is allowed. It may edit a draft's text, comment, and hand a draft on while it stays `draft`; the claim SQL excludes drafts. `WorkDraftRulePostgresTest`.
- **Registry changes (queues, agents, their queues, their sponsors) write no `work_event`**: events are per item or per project, and `work_event.project_id` is `NOT NULL`. Agent membership is a `member` event of its project. Each registry change (queue create/update/retire; agent register/update/rotate/retire/takeover/sponsor release) is logged and written to the wiki's admin audit trail through the `WorkAudit` port (`WikiWorkAudit` in the wiki, no-op by default): the person acting, the action (`work.queue.*`, `work.agent.*`) and the agent or queue, never a token; a failing audit never undoes the change. Every sponsor an agent has had is kept in the append-only `work_agent_sponsor_history`. Changes the module is not told about (a wiki group, the admin role, a deleted account) are caught by `WorkClaimsService.sweepStanding` (`SponsorSweep`, run by the claim sweeper each cycle after the expiry sweep; a sponsor whose lookup fails is skipped with one WARN per outage and nothing is ended). `WorkAgentRegistryPostgresTest`, `WorkSponsorStandingPostgresTest`.
- **The assignment log** (`assignmentLog`, `GET /api/work/log`) covers exactly the caller's visible projects: visibility is computed from the actor and applied in the one query that returns the rows; an agent filter leaks nothing. A `claim_expired` row is a system event: the "who" filter (`actorKind`) never hides it (P29). Cursor is `(at, id)`; index `idx_work_event_log` (V078). `WorkServiceAssignmentLogTest`, `JdbcWorkStoreAssignmentLogPostgresTest`.
- **Facades and the store split.** `WorkService` hands out `registry()` (`WorkRegistryService`: queues, agents, identity) and `claims()` (`WorkClaimsService`: claimable, claim, release, hand-off, sweep); the store is `WorkStore` plus `WorkCatalogStore` (projects, products, members; the member writers live in `JdbcWorkMembers`), `WorkRegistryStore`, `WorkClaimStore` (`store.claims()`) and `WorkCredentialStore` (`store.credentials()`). The split exists to keep each class under the PMD complexity limits without suppressions: do not fold a facade back into `WorkService` or add a suppression. `WorkServiceVisibilityPostgresTest` enumerates the facade methods (its `FACADES` set); a new `*Service`-returning accessor must be listed there.
- **Migrations**: V076 (queues, agents, agent-queue, claim columns, `assignee_queue`, attribution columns, `work` key scope), V077 (`work_agent_key_history`, dropped again by V080), V078 (`idx_work_event_log`), V079 (`work_agent.sponsor`, `work_agent_sponsor_history`, `work_agent_credential`), V080 (drops `work_agent.api_key_id` and `work_agent_key_history`), V081 (`work_change`, the `work_item` acknowledgement columns), V082 (`work_deployment`, `work_deployment_item`, `work_deployment_event`), V083 (`work_product_event`), V084 (`work_item.type`, `work_item.labels`), V085 (`work_sprint`, `work_item.sprint_id`, `work_item.estimate`), V086 (`work_event.tx`, `work_watch`, `work_notification`, `work_notify_cursor`, `work_notify_pref`, `work_webhook`), V087 (`work_saved_filter`), V088 (`work_attachment`, `work_attachment_blob`), V089 (`work_product_hook`, `work_codehost_identity`, `work_codehost_head`, `work_codehost_lifecycle`, and the code-host columns on `work_change`), V090 (`work_deployment.remediates_id` and three partial indexes for the flow and DORA reads; `idx_work_event_moves` replaced the unreleased draft's `idx_work_event_status`, dropped if present), V092 (`work_notify_skipped`, `idx_work_notification_created`), V094 (`idx_work_item_find_updated`, two partial deployment indexes for the DORA reads), V095 (`work_member_principal_nonblank_chk`, `idx_work_item_reporter_created`, `work_attachment_blob.content` stored `EXTERNAL`), V096 (`work_notification_reason_chk` replaces the inline reason check and adds `requested`). **There is no V093** (reserved by the hardening pass, never used); do not renumber.

## Changes and autonomy

Phase 3b. Plan: `docs/superpowers/plans/2026-11-16-work-management-phase3b-changes-autonomy.md` (its "Decisions" section lists what the owner approved where the design was silent).

- **One resolver of an item's policy.** `WorkAutonomy.resolve(PolicyChain)` gives the `EffectivePolicy` (`level`, `directAllowed`, `doneWhen`): the item's own level, else its nearest ancestor's, else the project's default, then capped by its product's ceiling; direct commits from the nearest value on the item or an ancestor, default off; done-means from the epic only. `WorkStore.policyChain(itemId)` loads what it needs. No other class reads `autonomy()`, `allowDirect()`, `doneMeans()`, `defaultAutonomy()` or `autonomyCeiling()` to decide anything (`WorkAutonomySourceRuleTest`; the stores, the patch applier, the event diff and input normalising only carry the columns). The resolved record's accessors are named differently on purpose so the rule can tell them apart. It is resolved afresh on every gated call: never cache it. `WorkAutonomyTest`, `WorkAutonomyPostgresTest`.
- **The gates restrict agents only.** `WorkGates`: approve as ready (out of `draft`, `refining` or `cancelled` to anything later: `autonomous` only; without `cancelled` an agent could cancel refined work and bring it back as ready), close (to `done`: not at `supervised`), review (never a change the agent opened or put a commit on: `work_change.head_agent_ids` records every agent that set a head), merge (never its own in that same sense; not at `supervised`; not when the standing approval is another reviewer's; a change with no approval for its current commit is the conflict `not_approved`, answered by the service), direct commit (needs `allow_direct` and a level above `supervised`). A person is never refused at a gate. `WorkPolicy.mayChangeStatus` applies approve and close to item moves; a draft keeps its two older refusal texts. Every gate decision for an agent is reported once through `WorkScopes.decide` (`wikantik_work_gates_total{gate,outcome}`). `WorkGatesTest` (the table), `WorkItemGatesPostgresTest`, `WorkGateMetricsPostgresTest`.
- **Who sets the policy fields** (`ItemGates.requirePolicyChange`): an agent none; `doneMeans`, `allowDirect` and the `autonomous` level a lead; anyone else who may edit the item may only tighten: name a level stricter than it inherits, or tighten or clear one a lead loosened. Naming the level it already inherits is refused (an own value would outlive a lead tightening the epic). A move to another parent or product that leaves the item looser, or with direct commits it did not have, is the same loosening (`requireNoLoosening`): a lead, never an agent. `WorkPolicyFieldsPostgresTest`.
- **Changes** (`work_change`, V081; `WorkChangesService` via `WorkService.changes()`, `WorkChangeStore` via `store.changes()`): open, in review, merged or abandoned; rows are never deleted. Every write locks the change row, checks it is live (`change_closed` otherwise), runs the caller's decision **on the locked row** (`Check` / the merge `Function`), updates and writes one event on the item. Keep gate decisions inside that callback: a decision on the service's earlier read can approve a merge of a commit that has since moved. An approval names the commit it approved (`reviewed_head_sha`); a new head clears it; an agent may merge only while its approval stands on the change's current head; the merged sha may be a squash or merge commit (`not_approved` when no approval stands on the head). Merge kinds: `reviewed`, `unreviewed` (a person, no standing approval), `direct` (opened and merged in one call: one `change_merged` event). A change needs the item to target a product and keeps that product for good. Change events carry `from_value` `change:<id>`. A change is as hidden as its item: an unknown id and an unseen one are the same `WorkNotFoundException`. `WorkChangeGatesPostgresTest`, `WorkChangeRacePostgresTest`.
- **A live change holds the item**: it cannot move to `done` and cannot change product (`open_changes`), for everyone. This is checked in the item write with the item row locked (`JdbcWorkItemWrites.requireNoLiveChange`), and opening a change takes `FOR SHARE` on the same row and refuses a closed item, so the two cannot cross.
- **Every change write reads the item under a share lock** (`JdbcWorkChanges.lockItem`, after the change row is locked): an agent is fenced there if another agent holds the item (`ClaimFenceException`, answered by `WorkChangesService.fenced` as the usual denial), and `open` refuses with `stale` when the item's product is no longer the one the service read. Lock order is change row, then item row; the item write locks only the item row, so there is no cycle. An update that changes neither the commit nor the link writes nothing; an empty review URL clears it.
- **Agents' change writes are fenced like item writes** (`OPEN_CHANGE`, `REVIEW_CHANGE`, `MERGE_CHANGE` are `Action.fenced()`): refused while another agent holds the item's claim. So a reviewer must hold the item before it reviews.
- **Acknowledgement.** An agent's close at `autonomous` sets `work_item.ack_required` in the same statement as the status (`writeItem(…, ackRequired)`), on any move into `done` (from `cancelled` too, which is "closed" but not done); a move out of `done` clears it and the acknowledgement. `WorkService.acknowledge` (a human member; an agent is refused) records who and when with one `acknowledged` event; `ack_required` stays true as the record of how the item was closed. `waitingOn` lists what still waits (reason `acknowledge`) to the project's leads and to admins. `WorkAcknowledgePostgresTest`, `JdbcWorkStoreAckRollbackTest`.
- **`ItemView`, `ItemSummary` and `Item` were unchanged by phase 3b** (`Item` gained `type` and `labels` in V084 and `sprintId` and `estimate` in V085, below). The effective policy and ack state come from `WorkService.policyOf`, changes from `changes().views`, board badges from `changes().counts`. Do not fold them into the item view: it is built in every mock-based test.
- **Class splits made for the complexity limits** (no suppressions): the item write is `JdbcWorkItemWrites`, the autonomy checks are `ItemGates` (reached through `WorkScopes.gates()`), acknowledgement is `Acknowledgements` and `JdbcWorkAcks`.

## Deployments

Phase 4. Plan: `docs/superpowers/plans/2026-11-16-work-management-phase4-deployments.md` (its "Decisions" D1–D11 were approved by the owner).

- **A deployment has no project.** It is one product version going to an environment, carrying items (`work_deployment`, `work_deployment_item`, V082). Its history is its own append-only table (`work_deployment_event`), because `work_event` needs a project; each carried item still gets `deployment_requested`, `shipped` and `rolled_back` events (`from_value` `deployment:<id>`).
- **It is seen through what it carries.** `DeploymentAccess` is the only place deployments meet standing: it asks `WorkStanding` for the actor's role in every project a carried item belongs to. A caller who can see none of the items gets `WorkNotFoundException`, the same as for an unknown id. `WorkDeploymentsService` hands out `DeploymentView`s whose `deployment.itemIds()` holds **only the visible items**: never return a raw `Deployment` from the store to a caller, or hidden ids and their count leak. `WorkDeploymentAccessPostgresTest`.
- **States only move forward** (`DeploymentState.mayBecome`): requested, approved, running, verified or failed, then rolled back; requested or approved may instead become rejected (the requester withdraws it, or someone who may approve turns it down; without this the only way to clear a mistaken request was to approve it, which opens the script gate). A deployment carries only items that are `ready` or later and target its product. The store decides the move on the locked row (`bad_transition`). Verified needs non-blank evidence (the service and a table CHECK both say so); evidence is plain text and no surface may render it as markup.
- **The deploy gate** (`DeployGates.mayApprove`) is the product's `deploy_gate`, never the autonomy level: `human` = an admin or a person who leads every carried project; `agent` = also any member of every carried project. Requesting and running take membership of every carried project. An agent's approval decision is reported as gate `deploy`.
- **Done means in production.** `ItemGates.requireStatusChange` returns `CloseRules(ackRequired, needsDeployment)`; `needsDeployment` is true for any actor closing a story or task whose epic's done-means is `in_production`. The store checks for a verified deployment with the item row locked (`JdbcWorkItemWrites.requireShipped`, conflict `awaiting_deployment`). "Shipped" (`JdbcWorkDeployments.shippedVerified`) means: environment `production`, state verified, verified at or after the item's last merged change, and a deployment of the product the item targets now. A rolled-back deployment no longer counts; an already closed item stays closed. **Leaving the epic is a loosening**: `ItemGates.requireNoLoosening` treats a move that takes an item from `in_production` to `merged` like a looser level (a lead, never an agent); keep any new way of changing an item's parent behind it.
- **`gate(actor, id, version)`** is what the deploy script asks (`GET deployments/{id}/gate`), answered from one read: approved only for the same version in state approved or running, with the state, version and environment it was taken from (the script compares the environment). `cleared` is its boolean. It reads committed state, so an approval or failure not yet committed changes nothing. `WorkDeploymentRacePostgresTest`.
- **`wikantik_work_deployments_total{state}`**: no product label.
- `closed_at` is set by every state that ends a deployment (`DeploymentState.ended()`: verified, failed, rejected, rolled back). `forProduct` reads a page at a time until it has the visible deployments asked for. What a caller may type is checked in `DeploymentInputs` (split from the service for the complexity limit).
- **A sponsor change replaces the sponsor the caller read** (`setSponsorAndRelease(agentId, expectedSponsor, …)`, conflict `stale` otherwise), and the standing sweep releases a claim only while the agent still has the sponsor it judged (`releaseForStanding(projectId, agentId, judgedSponsor, …)`). Creating a project or product whose key exists is `WorkConflictException` `exists` from the insert itself (`ON CONFLICT DO NOTHING`).
- **Type and labels** (V084): `work_item.type` is `feature|bug|chore` (an epic is always `feature`, refused otherwise in `ItemPatchApplier.validateShape`); `work_item.labels` is a sorted, lower-case `TEXT[]` of at most 10 names matching `^[a-z0-9][a-z0-9._-]{0,39}$`, validated only by `Labels.normalise` (a filter's labels too, in `ItemFilter`). There is no label table: `WorkService.features().labelsOf` (`WorkFeatures`, the holder every later feature facade hangs from, because `WorkService` is at the PMD method limit of 40) aggregates non-cancelled items, at most 200. A change writes one `field` event (notes `type`, `labels`; labels comma-joined, none as null; the same set reordered or re-cased writes none). `Item`, `ItemDraft` and `ItemFilter` have only their canonical constructors, so a construction site cannot silently drop the two fields. Classes split out for PMD: `ItemRules`, `JdbcWorkLabels`, and `WorkFilters` in wikantik-rest. `JdbcWorkStore` is at the GodClass boundary: put new store methods in a split-out `Jdbc*` class, not in it.

## Sprints and estimates

Small teams, part 2. Plan: `docs/superpowers/plans/2026-11-21-work-team-02-sprints-and-estimates.md` (its "Decisions" P2-1 onward say what was settled).

- **Schema and doors.** V085: `work_sprint`, `work_item.sprint_id`, `work_item.estimate`. Reached as `WorkService.features().sprints()` (`WorkSprintsService`) and `store.sprints()` (`JdbcWorkSprints`; transitions in `JdbcSprintTransitions`, history reads in `JdbcSprintHistory`). `WorkService`, `JdbcWorkStore` and `WorkPolicy.may` are at their PMD limits: new facades go on `WorkFeatures`, new SQL in a new `Jdbc*` class, agent refusals in `WorkPolicy.agentRefusal`.
- **Who may do what.** `MANAGE_SPRINT` (create, edit, start, close) is a lead's; `PLAN_SPRINT` (setting an item's `sprint`, gated in `ItemGates.requireFieldGates`) is a member's. An agent is refused both with "A person plans a sprint." Estimating is `EDIT_ITEM`, so an agent may estimate. Stories and tasks only: an epic is never in a sprint and has no estimate (its points come from `GET items/{key}/points`).
- **One active sprint** per project (`idx_work_sprint_active`; the conflict is `sprint_active`). A closed sprint takes no items and does not change; an item may leave it (`sprint_closed`). Starting and closing write the four figures on the sprint row (committed and completed, items and points): they are the record of the promise and are never recomputed.
- **Lock order: sprint rows, then item rows.** An item write takes `FOR SHARE` on its sprint rows first (`lockSprints` in `JdbcWorkItemWrites`); `start` and `close` lock the sprint rows, then the items. Keep it.
- **The close event precedes its moves, and the report cuts at event ids, never times** ("before the start" and "before the close" are decided by event id), so the close's own moves do not empty the last day.
- **`Burndown` is pure** and replays `field` (`sprint`, `estimate`) events and every status move as `StatusMoves` defines it (`JdbcSprintHistory` selects with `StatusMoves.movedSql`). Claims never move an item into or out of done or cancelled, so including them changes no figure; a new way to reach `done` must be added to `StatusMoves`. Days and weeks use the work clock's zone; `WorkWiring` passing `Clock.systemDefaultZone()` is the one place a zone is chosen.
- **No query assumes sprints exist.** The board's default to the active sprint is client-side only (the `sprint=` filter is `active|none|<id>`, parsed in `WorkFilters`). Claimable work lists active-sprint items first. Sprint events: `sprint_created`, `sprint_updated`, `sprint_started`, `sprint_closed`; their text is in `eventText.js`.

## Notifications (Part 3, V086)

- **The event log is the outbox.** The dispatcher (`WorkNotifyDispatcher`, run by `WorkDaemon` every `wikantik.work.notify.intervalSeconds`) reads `work_event` and writes `work_notification` rows; there is no second queue. Cursors (`work_notify_cursor`, `work_webhook.cursor_tx`/`cursor_event_id`) are `(tx, event_id)` over `tx < pg_snapshot_xmin(pg_current_snapshot())`, never a bare event id: an id cursor skips an event that commits after a higher id was read. The first dispatch starts from the newest existing event, so nothing from before notifications were switched on is ever notified. A webhook that resumes (flag back on, re-enabled, owner a lead again, taken over) also starts from the newest event, never a backlog.
- **One rule table, one auto-watch table.** `Recipients` decides who hears of an event and `AutoWatch` who starts watching; do not add a second place. Only the new assignee hears of an assignment; watchers hear of hand-offs; a mention beats a watch; the actor never hears of their own action. Sprint events, plain `field` edits and change/acknowledge/deployment events notify nobody. A comment event names its comment in `to_value`; its mentions are "current rows minus those already notified".
- **Standing is re-checked** with `WorkStanding.seesProject` at dispatch, at email time and at read (through the visible-project set). Agents are never recipients (the registry refuses an agent name the user directory knows as a person; where a collision already exists the person wins). Preferences write no event.
- **Webhooks** act for an owner lead, go through `WorkOutbound` (`EgressGuard` on every hop, https only), never return the URL or secret after creation, and are switched off after 24 h of failure. A new item event type must be added to `WebhookPayloads.SENDABLE` and `NoticeText`.
- **Structure.** `WorkStore.notifyStores()` returns a new `WorkNotifyStores` holder on every call, so the stores in it hold no per-instance state. `WorkFeatures` takes a `FeatureDeps` record (the constructor parameter limit); reach `notifications()` and `webhooks()` through `WorkService.features()`. The project key `INBOX` is reserved.
- **A poison event is skipped, a transient failure is not (V092).** A batch that fails inside facts/plan/notice insert rolls back and its events are retried one per transaction (`JdbcNotifyDispatch`). An event that still fails is skipped only if `TransientFailure` calls it poison (a non-SQL planning exception, or a `SQLException` of SQLSTATE class 21/22/23/42/0A); the cursor moves forward-only past it, a row goes into `work_notify_skipped` (no FK, message truncated to 500, NUL stripped), an ERROR is logged and `wikantik_work_notify_skipped_total` counts it. **Default is transient**: a null or other SQLSTATE, `WorkUnavailableException`, connection, timeout, IO or interrupt errors anywhere in the cause chain rethrow and retry next cycle and never skip (pool exhaustion must not eat events). Failures outside event processing (cursor lock, fetch) are never skipped. A skipped event is never re-notified.
- **Notification retention.** The dispatcher thread prunes `work_notification` (by `created_at`) and `work_notify_skipped` (by `skipped_at`) older than `wikantik.work.notify.retentionDays` (default 180, 0 = keep) in bounded batches, at most daily, and again next cycle while a table still had a full batch (`WorkNotificationStore.prune` returns `Pruned(deleted, more)`). The effective floor is 3 days (`MIN_RETENTION_DAYS`): the e-mail window is 48 h and pruning must not disturb it. These are derived rows, not work records; `work_event` is still never pruned.
- **Metrics:** `wikantik_work_notifications_total{channel,outcome}`, `wikantik_work_dispatcher_alive` and `wikantik_work_notify_skipped_total` (no labels); none has a project label.
- **Tests.** Dispatch tests wait with `DispatchAwait` (bounded, no fixed sleeps) and use a controlled `Clock`; tests never send real mail or make an outbound call (ports are fakes).

## Find and saved filters (Part 4, V087)

- **Facade.** `find()` is on `WorkFeatures` (`WorkService.features().find()`, `WorkFindService`), not on `WorkService`, which is at the PMD method limit. The stores sit on `store.notifyStores()` (`finder()`, `filters()`); that name now covers more than notifications.
- **Visibility.** The projects a find may search come from `WorkStanding` (`visibleProjects`) and are bound into the one statement as `project_id = ANY(?)`. A project the caller names but cannot see gives no rows, never an error.
- **Cursor.** `(sort value, id)`, bound to its sort. It is validated, not signed: a bad or foreign cursor is a 400 field `cursor`. It carries no visibility, so it never widens what the next request may see.
- **`me`** is resolved when the query runs (an agent's `me` is its claim holder and own items; agents have no watching).
- **`FindParams` is the only parser of the URL form**, and saved filters store that same form.
- **A shared filter searches its own project only** and is always run for the person who runs it. Saved-filter writes write no `work_event` (a preference table whose rows may be deleted).
- **`GET /api/work/items` has two modes, chosen by `project`:** with it, one project's list; without it, find. `FIND` is a reserved project key.

## Attachments (Part 7, V088)

- **Schema.** `work_attachment` (metadata: item, optional comment, file name, stored type, size, sha256, uploader, `removed_at`) and `work_attachment_blob` (the bytes, one row per attachment). The bytes live in PostgreSQL. `DELETE` is granted on the blob table only: the metadata table is UPDATE-only, so nothing is ever hard-deleted from it.
- **Reachable only through its own item.** Every service call resolves the item first (`scopes.itemScope`: unknown or invisible is the one 404), and the store puts both the item id and the attachment id in the `WHERE`. Another item's id, a removed id and an unknown id are the same 404. Never load an attachment by id alone.
- **Doors.** `WorkService.features().attachments()` (`WorkAttachmentsService`: `list`, `listing`, `mayAttach`, `upload`, `content`, `download`, `remove`, `maxFileBytes`) and `store.notifyStores().attachments()` (`JdbcWorkAttachments`). Add no method to `WorkService` or `WorkStore`.
- **Type from the bytes.** The stored type comes from `FileKinds.detect` (magic bytes), never from the uploader's claim or file name. Only PNG, JPEG, GIF and WebP are served inline; everything else is an `application/octet-stream` download. Every download carries `X-Content-Type-Options: nosniff` and a `sandbox; default-src 'none'` CSP added beside the site's; inline images get `private, max-age=300`, everything else `private, no-store`. `FileKinds.safeName` cleans the name.
- **Writes.** `ATTACH` (member, not management; agents are fenced by another agent's claim; a viewer is refused). An upload locks the item row `FOR NO KEY UPDATE` and checks the per-item total (live attachments only) in the same transaction; the per-file limit is checked before. Both limits come from `WorkSettings` (`wikantik.work.attachments.maxBytes`, `.maxItemBytes`) and refuse with 413: `reason: too_large` (one file over the per-file limit) or `reason: item_full` (the item's total would pass the per-item limit).
- **Reporter share (V095).** A reporter-only uploader's own uploads on one item are capped by `wikantik.work.attachments.reporterItemBytes` (default 10 MiB, never above `maxItemBytes`), checked under the same item lock; refusal is 413 `reason: reporter_full` (`WorkConflictStatus` maps conflict reasons to statuses). **Removed files still count** (otherwise upload/remove churns unbounded storage) and members are not held to it.
- **Downloads stream.** REST calls `WorkAttachmentsService.download`, which resolves scope exactly as `content()` does (404 before anything is sent) and reads the stored bytes with `substring(content from ? for ?)` in 256 KiB pieces (`CHUNK_BYTES`), so heap is bounded by a piece, not the file. No REST route calls `content()` any more. A failure after the headers went out cannot become a clean error. Upload still holds the file in heap, bounded by `maxBytes`.
- **Remove** is the uploader or a lead/admin (an agent removes only its own). It deletes the blob row and keeps the metadata row (`removed_at`) and the events. `list` shows live attachments only.
- **Events.** `attached` and `attachment_removed` notify nobody, are not sendable by webhooks and are not in `WorkEvent.ALL_TYPES`.
- **Render token.** `work-attachment:<id>` in item text is rewritten by `WorkAttachmentLinks` through `Context.VAR_LINK_TARGET_REWRITE` to that item's own download route. It is a string function and must never look anything up; `VAR_VIEWER_SENSITIVE` stays set so the per-item operator never reaches the shared render cache.
- **Tests.** `WorkAttachmentIT` (wikantik-it-test-rest) sets the two limits small in `it-rest-cascade.properties`.

## Code host (Part 5, V089)

- **Receive only.** Nothing calls GitHub and no GitHub token exists. A code host posts signed deliveries to `/api/work/hooks/{product}/{github|generic}` (REST: `WorkHookResource`, adapters `GithubHookAdapter` and `GenericHookAdapter` turn a body into neutral `CodeEvent`s; no adapter or servlet class lives here). The service is `WorkService.features().codeHost()` (`WorkCodeHostService`: `authenticate`, `apply`, `rejected`, `enableHook`, `disableHook`, `hooks`, `acknowledgeFlag` is on `changes()`); the stores are on `store.notifyStores().codeHost()` (`WorkCodeHostStore`, `JdbcWorkCodeHostStore` delegating to `JdbcWorkCodeHost*`). Add nothing to `WorkService` or `WorkStore`.
- **Hook check order, and the identical 404.** Method and path, work and flag on, then the declared body size (413, nothing read), then the signature header's shape (`HookSignature.wellFormed`: `sha256=` + 64 hex; missing or malformed is the same 404 with the body never read and no product looked up), then the capped body read (413), then `authenticate` (always the same two reads and exactly one HMAC, a dummy key and id `-1` when the product is unknown or has no live hook), then content type (415, only for a signature-verified form body), then parse, translate, `apply`. Every failure before the 413 and every signature failure is the **same 404 bytes and headers** (unknown or archived product, no hook, disabled hook, missing or wrong signature, wrong algorithm prefix, any method but POST): never add a distinguishable answer. Refusals before the signature verifies log at DEBUG only and echo nothing raw; `wikantik_work_codehost_rejected_total{reason}` (`HookRejection`: `too_large`, `no_signature`, `signature`, `form_encoded`, `unparseable`, `untimed`; no product label; unknown product, no hook and wrong signature are all `signature`) counts them. Refusals of a *verified* delivery (415, unparseable, untimed) keep WARN/INFO: only a secret holder causes them. The route is covered by `RateLimitFilter` on `/api/*`, keyed on `getRemoteAddr()` only, which is the real client only because Tomcat's `RemoteIpValve` rewrote it. Known limit: `docker/config/server.xml` leaves `internalProxies` at Tomcat's default (any private-range peer is trusted), so a LAN or docker-network host can set the client-IP header, and `127.0.0.1` makes the request loopback, which `RateLimitFilter` exempts. Restricting `internalProxies` to the proxy is an open follow-up (WikantikOperations 1.19). `apply` takes a `HookDelivery` that only `authenticate` can create, and is called even for a ping or an empty translation so `last_received_at` moves.
- **One pull request is one change.** `(item, review_number)` is unique (`idx_work_change_review`): a close abandons the row, a reopen revives it, no splitting and no rewinding. Lifecycle (opened, reopened, closed, merged) is a last-writer-wins register keyed by the **code host's own time**, then rank merged > closed > reopened > opened; **merged is terminal**. Receipt time is never an event time: a delivery holding an event with no usable time (a generic event without `at`) is rejected whole. The rules are written once in the Javadoc of `JdbcWorkCodeHost`.
- **The code host never moves an item.** No code-host path writes `work_item` (status, assignee, sprint and version stay as they were). It only fills in change records of items that target the hook's product.
- **Attribution is by the host-asserted pusher only (M-1).** A push (direct or to a branch) is attributed through the identity mapping to `CodeEvent.actor` (GitHub's `sender.login`, never the `pusher` object or a commit), for `opened_by`/`merged_by` alike (`CodeHostApplier.pusher`). A commit's author or address is never used for attribution; commit authors only teach the username mapping (`CodeHostIdentities.teach`, only with a host-asserted username and a usable address). The mapping trusts the wiki profile e-mail to be the user's own (Security.md); a commit address alone never decides who a change is attributed to. An unmapped pusher is an outside author; no pusher is `unknown`. A generic sender must send `actor` on a push to be attributed. Changes recorded before this keep their old commit-address attribution.
- **Identity by email, usernames only from host-asserted fields.** `CodeHostIdentities` matches a wiki account by profile email (case-insensitive, exactly one account, never a `@users.noreply.github.com` address). A host username is learned only from an account field the host sets (`login`, a push commit's `author.username`), never from a commit's free-text name or address; first mapping wins. A mapping is only as trustworthy as two things outside the wiki's control: GitHub setting a commit's `author.username` only for an address verified on that account, and a wiki profile address belonging to its user; every commit author in a push can teach a mapping, so a wiki user whose profile names someone else's GitHub address (unused by any other wiki account) would have that person's later code-host activity attributed to them. Someone with no match is an outside author (`external_*_by`), shown as "<name> (outside the wiki)" and never linked.
- **System actor.** `Actor.Kind.SYSTEM` (login `codehost:github`) has no standing and is refused by every store writer except the `JdbcWorkCodeHost*` classes; its events render as actor `GitHub`, `actorKind: system` (`Actor.label`).
- **Flags** (`work_change.policy_flag`, set only by a code-host merge): `unreviewed` (a merge with no approval of the merged commit, not the author's own, stamped no later than the merge) and `direct` (a direct commit where `allowDirect` is off). A lead acknowledges (`acknowledgeFlag`, `Action.ACKNOWLEDGE_FLAG`); the lane is `WaitingItem.CHANGE_OUTSIDE_POLICY` ("merged outside policy"), and `change_flagged` notifies the project's leads (`Recipients`, reason `acknowledge`) but is not webhook-sendable. **Late-approval clearing:** a host approval of the merged commit stamped no later than the merge, arriving after it, turns an `unreviewed`, unacknowledged, non-superseded change into `reviewed` and removes the flag (one `change_reviewed` event with the note "approved before the merge; no longer outside policy"); an acknowledged flag and an approval stamped after the merge never clear. Events are append-only and notice rows are never deleted; instead **a `change_flagged` notice is live only while its flag waits** (`FlagNotices`: flagged, unacknowledged, not superseded). The inbox, unread count, mark-all-read (`JdbcWorkNotifications.READABLE`) and the email digest (`JdbcNotifyEmail.PENDING`) all apply `FlagNotices.liveNoticeSql`, so a cleared, superseded or acknowledged flag disappears for every lead whichever of the dispatch and the clearing delivery came first (`WorkFlagNoticesPostgresTest`); the flagged lane uses the same `FlagNotices.waiting`. Acknowledging a cleared or superseded flag is 409 `not_flagged` with a message saying it was already cleared.
- **`superseded_by` rows count nowhere.** A direct commit that a pull request's merge replaces is marked `superseded_by`; the flag lane already excludes it and **every count over `work_change` (Part 6) must too**.
- **Concurrency.** Every code-host transaction, and an agent's or person's `open` of a change, first takes `pg_advisory_xact_lock(1464550216, product_id)`, then locks `work_change` rows in id order, then the item `FOR SHARE`; the order is written once in `JdbcCodeHostRows`. Deliveries of one product queue behind each other.
- **Bounds.** Each head report prunes a change's `work_codehost_head` rows to the 200 most recent reports and approvals by host time, plus its current head and the host's newest head report (at most 202 rows); an approval prunes nothing, so an approval that arrives before its commit's push still stands when the push arrives. Outside the guarantee: more than 200 later-stamped reports or approvals, interleaved with head reports, arriving before a commit becomes the head can drop that commit's approval, and its redelivery then logs a second `change_reviewed`. `work_codehost_lifecycle` keeps 200 events per change; past that nothing more is logged and a close that loses the register moves nothing. Host times are clamped to the work clock and to 1970-9999. **The register rows are not pruned by age and no retention key exists (M-4, accepted):** they are what makes a redelivery write nothing (deleting them and replaying logs a second `change_abandoned` and `change_reviewed`), and every register row pairs with an append-only `work_event` row, so pruning would not bound growth anyway.
- **Outside the order guarantee.** Fixed: on a closed item a close that loses the register to a later reopen still raises `closed_at` of the abandoned change to the latest close (`laterClose`, only when that delivery logged its close event), so the state is abandoned in every order. Accepted (characterised in `WorkCodeHostOrderLimitsPostgresTest`): a person reopening the item afterwards does not revive a change the host reopened meanwhile; a push stamped after a merge that arrives before it is a head report of the still-live change, not a new change (splitting a change is forbidden); a pull-request number reused after a merge lands on the merged change (GitHub never reuses numbers within a repository).
- **Secret.** Stored as issued, shown once (`HookCreated.toString()` prints `secret=***`), rotated by turning on again; never in a product event, audit detail, log line or history.
- **Tests.** `WorkCodeHostIT` (wikantik-it-test-rest) signs its own deliveries; `it-rest-cascade.properties` turns the endpoint on and sets `wikantik.work.codehost.maxBodyBytes = 65536`.

## Flow and DORA metrics (Part 6, V090)

- **Computed at read time; nothing is stored.** `WorkFeatures.flow()` (`WorkFlowService`: `project`, `dora`, `doraForProduct`; not on `WorkService`, which is at the PMD method limit) answers every request from the work tables. No table, cache, materialised view or Prometheus series carries a figure, and none may be added: `WorkFlowNoStoreRuleTest` fails on any write verb in the flow store's SQL and on any flow or DORA class that registers a metric with a metrics library. The figures are product figures; telemetry-for-observation belongs to jakemon.
- **Layers.** `JdbcWorkFlow` (behind `store.notifyStores().flow()`, the LAST component of `WorkNotifyStores`) is `SELECT`-only and returns facts (`ClosedItem`, `OpenItem`, `DeploymentFact`, `RecoveryEnd`, `ChangeFact`); `Flow`, `Dora`, `DoraReports`, `Percentiles` and `MetricWindow` compute from them and never see SQL. Percentiles are nearest rank in integer maths (`(p * n + 99) / 100`, never `Math.ceil` of a float; `PercentilesTest` pins n=20, p=85 to rank 17). Durations leave as whole seconds; rates are `{numerator, denominator}` and an empty window is 0 of 0, never NaN.
- **Zone.** Weeks start Monday 00:00 in the **work clock's** zone (`clock.getZone()`, which production passes as the server default; it is not UTC). SQL receives only instants computed in Java; no `date_trunc` or `AT TIME ZONE` in the flow SQL. A window is at most 366 days (`LOOKBACK`); an item or change older than that is outside every figure.
- **The visible project is bound into every statement.** A project route resolves its scope once (`scopes.scope`) and binds exactly that project id into each store call; a stranger never reaches a store call (404 identical to an unknown key). `doraForProduct` is wiki-admin only (`requireInstance`, 403). The only reads that cross projects are the product-wide recovery-end and "remediated" lookups; their outputs are a duration, a count and a boolean, never a key, id, version, title or person (`aRemediatorCarryingOnlyBsItemsStillMarksAsDeploymentFailed` asserts it).
- **Figures read change ROWS, not events.** Lead time, the merge mix and the flagged counts come from `work_change` columns (`first_commit_at`, `closed_at`, `merge_kind`, `policy_flag`, `flag_acknowledged_at`). `closed_at` is the winning merge time. **Rows with `superseded_by` set are excluded from every figure** (cross-part ruling R4; `aSupersededDirectChangeIsCountedNowhere`).
- **Lead time start is capped:** `min(openedAt, max(firstCommitAt, openedAt - 30 days))` (`DoraReport.MAX_COMMIT_LEAD`), because a rebased or cherry-picked pull request carries an implausibly old first commit. A change with no first commit starts at `openedAt` (`changesWithoutCommitTime`); one moved by the cap is counted in `changesWithClampedCommitTime`; a first commit after opening falls back to opening and is not counted there. The merge must be no older than 366 days before the window's start to be read.
- **Failure and recovery come from `work_deployment_event`**, because `work_deployment.closed_at` is overwritten by a later state (a verified deployment later rolled back). Failed = failed, rolled back (even after verifying) or remediated by a non-rejected deployment; rework = ran and itself remediates another; deployment frequency counts production deployments **verified** in the window, so one verified then rolled back counts. Staging never counts. Recovery ends at the earliest of the rollback, the verification of a remediator (any project of the product, Q10) and, only for a deployment that never went live, the next verified production deployment of the product.
- **`remediates_id`** (V090, nullable FK on `work_deployment`, `CHECK (remediates_id <> id)`, `idx_work_deployment_remediates`): set at request time only, in the same `INSERT`, so no cycle can form. `Remediation.check` refuses another product or normalised environment (blank means production) and a target that is not verified, failed or rolled back, naming `remediates`; an unknown target and one the caller cannot see are the same 404. V090 also adds the partial indexes `idx_work_event_moves` (the five event types that can carry a status move), `idx_work_deployment_verified` and `idx_work_change_merged`; no table, no grant.
- **Status moves by any route.** First start and last close are `StatusMoves.intoSql` (in progress, done): a hand-off to done is a close, a claim is a start. An item reopened after done counts nowhere until closed again, then once at its last close. **Cycle time = last close - first start - the time the item sat done** (each done move to the next move out, only intervals after the first start; `ReopenedTime.gap` over `StatusMoves.of`, `ClosedItem.reopenedGap`; no second definition of a move). Reopening to ready rather than in progress still counts the wait before restart; only done intervals are removed. Lead time (creation to last close) is unchanged and includes the done interval; an item that reaches done (by status change or hand-off) without ever being in progress has a lead time and no cycle time; a lapsed claim or release back to ready is neither a start nor a close (the first start stays the first).
- **`excluded` (negative lead time).** A change whose lead time computes negative is kept out of the figure but counted: `Dora.LeadTime.excluded`, `DoraReport.excluded`, JSON integer `excluded`, and `DoraPanel` shows a note when it is above 0.
- **Figures are as-of-now (accepted).** Computed from current rows at request time, so the same window read later can differ (an item reopened, a change superseded, a deployment rolled back). No snapshot, by design. A deployment that failed before going live counts as recovered at the next verified production deployment of its product: looser than DORA's time-to-restore, it measures time to the next successful release.
- **Indexes (V094).** Only the default find sort (`updated_at, id`, with its keyset cursor) is indexed (`idx_work_item_find_updated`); created, priority and due sorts still sort the matching rows (measured 4-5 ms for one project, 28-30 ms for ten, over 100k items). Do not add the other sort indexes without new measurements: each costs write amplification on `work_item`. The `remediated` statement carries `r.remediates_id IS NOT NULL` so the partial `idx_work_deployment_remediates` is usable; the two partial deployment indexes (`idx_work_deployment_started`, `idx_work_deployment_live`) are production-only.
- **Throughput is not velocity.** An item counts in the week of its last close, filtered by its current sprint; Part 2's velocity and sprint report are sprint-end snapshots. They need not match in general (P6-9), but for a sprint whose items all closed inside it they agree whatever route closed them (`velocityAndThroughputAgreeForOneSprint`). The merge mix is for the window; Part 5's flagged lane is all-time unacknowledged.
- **Tests.** Every test uses a fixed clock and SQL-set event times, never `Instant.now()`: `WorkFlowPostgresTest`, `WorkDoraPostgresTest` (each with a `Europe/Berlin` case), `FlowTest`, `DoraTest`, `PercentilesTest`, `MetricWindowTest`. `WorkServiceVisibilityPostgresTest` lists `flow` and `dora` as reads and `doraForProduct` as an instance read. REST: `WorkFlowRoutes` and `WorkFlowJson` inside the existing project and product resources (no new servlet); IT: `WorkFlowApiIT`.

## Intake (reporters, Part 8, V091)

- **A reporter is not a member.** `WorkRole.REPORTER` is the lowest role. A person (a user row, or a group row of a group they hold) whose only row in a project is `reporter` may file an item into it and follow the items they filed, and reaches nothing else. `WorkStanding.roleIn`, `seesProject` and `visibleProjects` return viewer-or-above only: they never return, count or sponsor-cap a reporter row, so every ordinary read answers a reporter as it answers a stranger (not found, empty, denied). A missed site therefore fails closed. `VISIBLE_PROJECTS_SQL` is an allow-list built from `WorkRole.STANDING`, never a deny-list.
- **The separately named checks.** A reporter is admitted only through `WorkStanding.mayFile`, `canSee(actor, item)`, `reportsOnly`, `followsAsReporter`, `reportOnlyProjects` and `reportableProjects`, reached through `WorkScopes.intakeScope` and `WorkScopes.ownItemScope`. All are person-only (`Actor.Kind.HUMAN`; an agent named like a reporter gets nothing). `WorkStandingSourceRuleTest` limits who may call the intake store's row reads. `ItemViews.view` throws for a reporter scope: a reporter never reaches a full view.
- **`intake()` is the only facade that answers a reporter.** `WorkService.features().intake()` (`WorkIntakeService`: `reportableProjects`, `submit`, `item`, `reported`, `comment`, `outsideReporters`). The store reads are behind `store.notifyStores().intake()` (`WorkIntakeStore`, `JdbcWorkIntake`, the V091 partial index). Intake adds no method to `WorkService` or `WorkStore`.
- **The reduced view is an explicit field list.** `ReportedItemView`, `ReportedItem`, `ReportedComment`, `ReportedEvent` and `ReportableProject` have components for exactly what a reporter may see and hold no `Item`, `Link`, `Change`, `Deployment`, `Sprint`, `Project` or `Member` (`ReportedItemViewTest`). REST (`WorkIntakeJson`) serialises them field by field. People are display names; there is no login, agent id, item id, project id or note in any of them. The discussion on their item is shown whole (decision D12: there are no internal comments), including members' comment text and agent author names. Item text is rendered with links as typed, so a key in a reporter's text names no other item's title.
- **`ReporterEvents` is the one allow-list and reshaping.** It decides which events notify a reporter (`commented`, and every status move as `StatusMoves` defines it) and rebuilds each with `note = null` and `agentId = null` (a status move becomes `status` with only the two status words). Dispatch (`Recipients.forReporters`, `NoticePlanning`), the inbox, the unread and mark-all-read SQL (`notifiedSql`), email (`NoticeText.reporterLine`) and the item timeline all use it, and `theInboxSqlAndTheJavaRuleAgree` compares the SQL and the Java rule over every `WorkEvent` constant. A new event type reaches members only until it is added there on purpose. Attachments notify nobody. **A request reaches the leads (V096, reason `requested`)**: `NoticePlanning.requestLeads` adds every lead when a person with no standing in the project who follows the item as its reporter files it (`created`), or comments on it while it has no assignee (`Recipients.forRequest`); a member's own new item is no request, and the notice line is "filed a request" (`NoticeText`).
- **Standing is per item for notices.** A reporter-only person hears of an event only on an item they reported, re-checked at dispatch and at send time. Caches are keyed by project, login and item, never by project alone. Humans only; an agent can never be a reporter (`WorkInputs.requireAgentRole`, the V091 agent-role CHECK, the `FILE_ITEM` agent refusal in `WorkPolicy.agentRefusal`).
- **Filing.** `Action.FILE_ITEM`; an intake item always starts `draft`; `level` is story or task (an epic is refused); the form takes `projectKey`, `level`, `type`, `title` and `body` only, and a member-only field is a 400 naming it. Body and comment are capped at 20,000 characters (`WorkIntakeService.MAX_TEXT`). Filing is capped per reporter: `wikantik.work.intake.maxPerDay` (default 20, 0 = no cap) in a rolling 24 h counted over every project and human filings only, for reporter-only callers only (members are uncapped); the next is 429 `reason: intake_limit`. Count and insert are one transaction under `pg_advisory_xact_lock(hashtextextended('work-intake:'||login,0))` (`WorkIntakeStore.createWithinDailyCap`, an `ItemGuard` run first inside `JdbcItemCreate`), so a parallel burst cannot pass the cap. The count covers everything the login reported, including filings in projects where they are a member. A lead can still stop a reporter by removing the row. "Reported from outside" is computed (`outsideReporters`, bounded by the logins in the response), never stored. `SUBMIT` is a reserved project key.
- **A new public service method must be classified for reporters.** Put it in `READS`, `WRITES` or an own-item set of `WorkServiceVisibilityPostgresTest`, which drives every public method of `WorkService` and each facade as a reporter and fails on any answer but not found, denied or empty. The REST leak sweep is `WorkIntakeIT` (wikantik-it-test-rest).
- **A reporter never receives a user id.** Item body and comments reach a reporter through `WorkPeople.displayForReporter`, which rewrites every `[@]name(user:<anything>)` token to `@Name` (past 50 distinct ids, or for a malformed id, nothing is looked up and the token's own snapshot name is used); text and `bodyHtml` are both made from the reshaped Markdown (`ItemViews.reporterBody`/`reporterComment`). Members get the stored text. Never render reporter HTML from the stored body.
- **Blank principals are refused (V095).** `work_member.principal` has `CHECK (principal !~ '^\s*$')` (added `NOT VALID`, validated only when no blank row exists, else a NOTICE), `putMember` refuses a blank with a validation error, and `JdbcWorkMembers.agentPrincipal`/`userPrincipal` return SQL NULL, never `""`, so a blank can match no actor. `JdbcWorkClaims` uses the same helpers.
- **Accepted: ids reveal volume.** Item keys are per project, but attachment, comment and event ids come from global sequences, so anyone who sees any of them can infer how much work the whole wiki has done. Ids never grant access: every read names the item as well.
- **V091** replaces the role CHECK to allow `reporter`, adds a CHECK that an agent row is only `viewer` or `member`, and adds a partial index on reporter rows. It fails, rolling back whole, on a database with an agent member row of role `lead`; see WikantikOperations section 1.21.
