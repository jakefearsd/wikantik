# wikantik-work

Module notes, loaded when working under this directory.

- **wikantik-work** (work management): projects, epics/stories/tasks, comments, queues, agents, claims and an append-only event log in `work_*` tables (`com.wikantik.work.*`). Depends on neither `wikantik-api` nor `wikantik-main`; all database access goes through `com.wikantik.jdbc.Jdbc`. Design: `docs/superpowers/specs/2026-11-15-work-management-design.md`.
- Feature flag `wikantik.work.enabled` (default `false`); `/api/capabilities` reports it as `work`.
- Work items never reach the page store, search index, bundles, sitemap, change feed or Page Graph. Nothing is hard-deleted; `work_event` is append-only.

Rules a future change must not break:

- No dependency on `wikantik-api` or `wikantik-main`. The runtime wiring and text rendering live in `wikantik-main` (`com.wikantik.work.runtime`).
- Every caller goes through `WorkService`; `WorkStore` has no visibility check (`WorkAccessArchTest` enforces it). `WorkServiceVisibilityPostgresTest` classifies every public `WorkService` method as a read or a write and drives each read as a non-member: a new public method must be classified there.
- Non-members get **404, never 403**, and lists omit the project. Wiki Admins see everything.
- Nothing is hard-deleted; `work_event` is append-only.
- `blocked_by` links are same-project only.
- Item text renders in the "links as typed" mode (`Context.VAR_LINKS_AS_TYPED`) with page filters off, and must never do a page, title, alias, heading or attachment lookup.
- No project, product or item labels on metrics (`WorkMetrics`): cardinality and leakage.
- The activity cursor is the pair `(at, id)`, never `at` alone.
- Sprints must stay addable as a new table plus nullable `work_item` columns; do not encode "no sprints" into queries, the board model or event types.
- The policy columns (`default_autonomy`, `autonomy_ceiling`, `deploy_gate`, `autonomy`, `done_means`, `allow_direct`) are stored and returned but inert until phases 3–4.
- Every state change leaves a `work_event` in the same transaction: item changes per field; membership (`member`, values `kind:principal:role`), project settings and archive (`settings`, field in the note) as project-level events with no item. Product changes are not recorded: `work_event.project_id` is `NOT NULL`.
- People are named by display name in both directions (`WorkPeople`): a request's assignee, member principal (kind `user`), board filter and bare `@name` mention resolve a display name; only a wiki admin's request may also use a login. Responses (`WorkJson`) show a non-admin display names only (`mine`/`self` mark the caller). Comment mentions use the wiki's token `@[Display Name](user:<id>)`; a resolved bare mention is stored as that token, so stored text never gains a login. At most 50 distinct mentions per comment resolve.
- Comments render through `WorkRenderer` like item text (`CommentView.bodyHtml`). Parent/product `field` events store ids; `EventKeys` shows keys at read time.
- An archived project is read-only: refusals are `WorkConflictException` with reason `archived` (REST: 409 `reason: archived`, no `current`); a stale version is reason `stale`.

## Agents, queues and claims

Agents are registered by an Admin, serve queues, are admitted to projects as `viewer` or `member` (never `lead`) and take items from a queue by claiming them. The agent endpoint is `/work-mcp` (`wikantik-work-mcp`); the same actions exist on `/api/work/*`.

- **Identity comes from the key binding and nothing else.** `WorkService.registry().actorForApiKey` is the only place an actor is derived from an API key: a key bound to an active agent is that agent; a key bound to a retired agent, or ever bound to an agent and since rotated away (`work_agent_key_history`, V077), is **no actor**; any other `work` key acts as its owner, with `admin` forced false. A caller never supplies `actor_kind`. `ActorTest`, `WorkAgentIdentityPostgresTest`, `WorkRegistryServiceTest`.
- **Agent keys are managed only through the registry.** The generic key endpoints (`/api/self/apikeys` rotate and revoke, `/admin/apikeys` revoke and bulk revoke) refuse, with 409 "This key belongs to a work agent. Rotate or retire the agent on the Agents page.", any key bound to an agent now or ever (`registry().agentNameForKey` / `isAgentKey`, system lookups with no actor; false when work is off); listings mark such keys `agentKey` (and `agent`, the name, for a registry reader). The label is not the discriminator. Deleting a person who owns an agent's key revokes it (the agent then has no actor; nothing is released, its claims lapse) and writes one WARN plus an admin audit entry naming the agent. `AgentKeyGuard` (REST), `SelfApiKeysResourceTest`, `AdminApiKeysResourceTest`, `UserDeletionServiceTest`.
- **Only a human can be an admin**, structurally: `Actor`'s constructor drops `admin` unless the kind is `HUMAN`. An agent sees only projects with an `agent` member row naming it, never its key owner's or a group's access. `WorkServiceVisibilityPostgresTest` drives an admin-flagged agent as a stranger.
- **Attribution is by id columns, never names.** Every store write by an agent records its id (`work_event.agent_id`, `work_comment.author_agent_id`, `work_item.reporter_agent_id`, `work_item_revision.edited_by_agent_id`), and the store refuses an agent actor without one. Compare agents by id. `JdbcWorkStoreAttributionPostgresTest`.
- **Claimable** means: the agent is a member of the project and serves the item's queue, the item is `ready` or `review`, unclaimed and not blocked. These conditions gate a fresh take only: the holder can always renew its own claim (removing a queue from an agent does not release claims it holds). `JdbcWorkClaimsPostgresTest`, `WorkClaimsServiceTest`.
- **A claim locks the agent row (`retired_at IS NULL`) and the agent's member row (role `member`) `FOR SHARE`, in that order, then the item**, inside the claim transaction. An agent retired, removed or demoted while it claims therefore cannot end up holding an item; the store, not only the service, enforces "no claim without access". Keep the lock order. `JdbcWorkClaimsConcurrencyPostgresTest`, `JdbcWorkClaimsAccessPostgresTest`.
- **Every ending of a claim writes an event in the same transaction as the change**, and the claim listener and `wikantik_work_claims_total` count every ending, so the metric agrees with the log. Releases write `released`: `from_value` is `agent:<holder id>`, `to_value` the resulting status, `note` the reason: `moved` (an item update), `reassigned` (a hand-off), `access removed` (member removed or demoted), `agent retired`, or a person's release note (`released` when none). A lapse writes `claim_expired`. A deliberate-release note equal to one of the four reserved words is refused (400), so a note can never pass for a consequence. Releasing or expiring touches only the claim columns, `status` and `version`. `WorkClaimListenerPostgresTest`, `JdbcWorkStoreHandoffRollbackTest`, `JdbcWorkClaimsRollbackTest`.
- **One assignment target per item**: a person (`assignee`, logins only) or a queue (`assignee_queue`). Setting one clears the other; create with both is refused. An item created with a person or queue writes `assigned`. `WorkServiceAssignmentPostgresTest`.
- **An agent may not move an item out of `draft`** (update or hand-off, every surface): "A person moves a draft forward." (`WorkPolicy.mayChangeStatus`). It may edit a draft's text, comment, and hand a draft on while it stays `draft`; the claim SQL excludes drafts. `WorkDraftRulePostgresTest`.
- **Registry changes (queues, agents, their queues) write no `work_event`**: events are per item or per project, and `work_event.project_id` is `NOT NULL`. Agent membership is a `member` event of its project.
- **The assignment log** (`assignmentLog`, `GET /api/work/log`) covers exactly the caller's visible projects: visibility is computed from the actor and applied in the one query that returns the rows; an agent filter leaks nothing. Cursor is `(at, id)`; index `idx_work_event_log` (V078). `WorkServiceAssignmentLogTest`, `JdbcWorkStoreAssignmentLogPostgresTest`.
- **Facades and the store split.** `WorkService` hands out `registry()` (`WorkRegistryService`: queues, agents, identity) and `claims()` (`WorkClaimsService`: claimable, claim, release, hand-off, sweep); the store is `WorkStore` plus `WorkCatalogStore` (projects, products, members), `WorkRegistryStore` and `WorkClaimStore` (`store.claims()`). The split exists to keep each class under the PMD complexity limits without suppressions: do not fold a facade back into `WorkService` or add a suppression. `WorkServiceVisibilityPostgresTest` enumerates the facade methods (its `FACADES` set); a new `*Service`-returning accessor must be listed there.
- **Migrations**: V076 (queues, agents, agent-queue, claim columns, `assignee_queue`, attribution columns, `work` key scope), V077 (`work_agent_key_history`), V078 (`idx_work_event_log`).
